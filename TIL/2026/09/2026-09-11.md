## 1. Servlet Filter와 OncePerRequestFilter

### Filter의 역할

Servlet Filter는 HTTP 요청이 `DispatcherServlet`과 Controller에 도달하기 전, 요청과 응답에 공통 처리를 적용하는 Servlet 기술이다.

인증·인가, 요청 로깅, CORS 처리, 문자 인코딩, 요청·응답 래핑 등에 사용할 수 있다. 여러 Filter가 등록되면 `FilterChain`에 정해진 순서대로 실행된다.

```text
클라이언트 요청
    ↓
Servlet Filter Chain
    ↓
DispatcherServlet
    ↓
HandlerInterceptor
    ↓
Controller
    ↓
Service
```

### `chain.doFilter()`의 역할

`chain.doFilter(request, response)`는 현재 요청을 다음 Filter 또는 최종 Servlet으로 전달한다.

```text
현재 Filter의 전처리
    ↓
chain.doFilter(request, response)
    ↓
다음 Filter와 Controller 실행
    ↓
호출 결과 반환
    ↓
현재 Filter의 후처리
```

응답을 직접 작성하고 요청 처리를 종료해야 하는 경우에는 `chain.doFilter()`를 호출하지 않고 `return`해야 한다. 응답을 작성한 뒤에도 호출하면 후속 Filter와 Controller의 처리가 계속될 수 있다.

### `GenericFilterBean`과 `OncePerRequestFilter` 비교

|구분|`GenericFilterBean`|`OncePerRequestFilter`|
|---|---|---|
|목적|Spring 환경에서 Servlet Filter를 편리하게 구현|Filter 내부 로직의 중복 실행 제어|
|상속 관계|Spring의 Filter 기본 클래스|`GenericFilterBean` 상속|
|구현 메서드|`doFilter()`|`doFilterInternal()`|
|중복 실행 제어|제공하지 않음|요청 속성을 이용해 제어|
|주요 활용|일반적인 커스텀 Filter|JWT 인증, 요청 로깅 등 요청별 실행 제어가 필요한 Filter|

### 중복 실행을 제어하는 원리

`OncePerRequestFilter`는 요청 객체에 해당 Filter가 실행 중임을 나타내는 속성을 저장한다.

```text
Filter 진입
    ↓
실행 제외 대상인지 확인
    ↓
이미 실행되었다는 요청 속성 확인
    ├─ 속성 존재 → 내부 로직을 생략하고 다음 체인 실행
    └─ 속성 없음 → 요청 속성 설정
                      ↓
                 doFilterInternal() 실행
                      ↓
                 finally에서 요청 속성 제거
```

기본 속성 이름은 Filter 이름에 `.FILTERED`를 붙여 만든다. 이 속성은 서버의 `HttpServletRequest` 객체에 저장되며 HTTP 헤더, 쿠키, Redis 데이터와는 관계가 없다.

### DispatcherType과 실행 범위

|DispatcherType|의미|
|---|---|
|`REQUEST`|클라이언트가 보낸 최초 요청|
|`FORWARD`|서버 내부의 다른 리소스로 요청 전달|
|`INCLUDE`|다른 리소스의 처리 결과 포함|
|`ERROR`|오류 처리를 위한 재디스패치|
|`ASYNC`|비동기 처리 이후 재디스패치|

`OncePerRequestFilter`의 “한 번”은 모든 디스패치를 합친 HTTP 요청 전체에서 무조건 한 번이라는 뜻이 아니다.

- `shouldNotFilterAsyncDispatch()`의 기본값은 `true`이므로 후속 `ASYNC` 디스패치를 건너뛴다.
- `shouldNotFilterErrorDispatch()`의 기본값은 `true`이므로 `ERROR` 디스패치를 건너뛴다.
- 두 메서드를 `false`로 재정의하면 해당 디스패치에서도 한 번씩 실행될 수 있다.
- Filter가 해당 DispatcherType에 매핑되어 있어야 실제 실행 대상이 된다.

### 설명용 예제

다음 코드는 JWT Filter의 기본 구조를 보여주는 예제이다.

```java
@Component
public class JwtAuthenticationFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(
            HttpServletRequest request,
            HttpServletResponse response,
            FilterChain filterChain
    ) throws ServletException, IOException {

        String authorization = request.getHeader("Authorization");

        // JWT 추출 및 검증 로직

        filterChain.doFilter(request, response);
    }
}
```

`Authorization` 헤더를 읽는 것만으로 JWT 인증이 완료되지는 않는다. 토큰 검증과 인증 객체 생성, `SecurityContext` 저장이 추가로 필요하다.

### 중복 실행처럼 보이는 상황

Filter 로그가 여러 번 출력됐다고 바로 중복 실행으로 판단하면 안 된다.

- `OPTIONS` 요청과 실제 `POST` 요청은 프리플라이트와 본 요청이라는 별개의 HTTP 요청이다.
- `/api/items`와 `/favicon.ico`도 서로 다른 요청이다.
- 전처리와 후처리에서 각각 로그를 남기면 한 번의 Filter 실행에서도 로그가 두 번 출력된다.
- `REQUEST` 이후 `ERROR` 또는 `ASYNC`로 다시 디스패치될 수 있다.
- Filter Bean을 Servlet 컨테이너와 `SecurityFilterChain`에 모두 등록하면 이중 등록 문제가 발생할 수 있다.

확인할 때는 HTTP 메서드, URI, `DispatcherType`, 스레드 이름, Filter 인스턴스를 함께 기록해야 한다.

> `OncePerRequestFilter`는 Filter의 모든 중복 문제를 자동으로 해결하는 클래스가 아니라, 요청 속성을 이용해 정해진 디스패치 범위에서 내부 로직의 재실행을 제어하는 클래스이다.

## 2. Spring Security의 Filter Chain 구조

### 인증과 인가

- 인증(Authentication): 요청한 사용자가 누구인지 확인하는 과정
- 인가(Authorization): 인증된 사용자가 해당 기능을 사용할 권한이 있는지 확인하는 과정

인증 정보가 만들어져야 사용자 권한을 검사할 수 있으므로 인증 Filter는 인가 Filter보다 먼저 실행되어야 한다.

### 주요 구성요소

|구성요소|역할|
|---|---|
|`DelegatingFilterProxy`|Servlet 컨테이너의 Filter 요청을 Spring Bean에 위임|
|`FilterChainProxy`|현재 요청에 적용할 `SecurityFilterChain`을 선택|
|`SecurityFilterChain`|요청 조건과 실행할 Security Filter 목록을 관리|
|`Authentication`|사용자, 자격 증명, 권한, 인증 여부를 표현|
|`SecurityContext`|현재 요청의 `Authentication`을 보관|
|`SecurityContextHolder`|현재 실행 흐름에서 `SecurityContext`에 접근|
|`AuthenticationManager`|인증 요청을 받아 적절한 인증 방식으로 전달|
|`AuthenticationProvider`|사용자 조회와 자격 증명 검증 수행|

```text
클라이언트 요청
    ↓
DelegatingFilterProxy
    ↓ Spring Bean에 위임
FilterChainProxy
    ↓ 요청과 일치하는 첫 번째 체인 선택
SecurityFilterChain
    ↓
인증 Filter
    ↓ Authentication 생성
SecurityContext 저장
    ↓
인가 Filter
    ↓ 권한 확인
Controller
```

여러 `SecurityFilterChain`이 존재하면 먼저 일치하는 체인 하나가 사용된다. 따라서 체인의 순서와 요청 매칭 범위가 중요하다.

### Security 설정 예제

다음 코드는 Authorization 헤더로 JWT를 전달하는 API를 가정한 설명용 예제이다.

```java
@Bean
SecurityFilterChain securityFilterChain(
        HttpSecurity http,
        JwtAuthenticationFilter jwtFilter
) throws Exception {

    http
        .cors(Customizer.withDefaults())
        .csrf(csrf -> csrf.disable())
        .sessionManagement(session -> session
            .sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/auth/login", "/api/auth/refresh").permitAll()
            .requestMatchers("/api/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated())
        .addFilterBefore(
            jwtFilter,
            UsernamePasswordAuthenticationFilter.class
        );

    return http.build();
}
```

`permitAll()`은 해당 요청을 인가 단계에서 허용한다는 의미이다. 그 경로가 앞쪽의 커스텀 JWT Filter를 아예 통과하지 않는다는 뜻은 아니다.

공개 경로에 토큰이 없을 때 JWT Filter가 바로 401을 반환하도록 만들면 `permitAll()` 설정과 관계없이 요청이 차단될 수 있다. 토큰이 없는 요청은 다음 체인으로 넘기고, 보호 경로 여부를 인가 단계에서 판단하도록 구성할 수 있다.

### 401과 403

|상태|의미|대표 상황|
|---|---|---|
|`401 Unauthorized`|유효한 인증 정보가 없음|토큰 누락, 만료, 서명 검증 실패|
|`403 Forbidden`|요청을 수행할 권한이 없음|일반 사용자의 관리자 기능 접근, CSRF 검증 실패|

> Spring Security는 하나의 Filter가 모든 보안을 처리하는 구조가 아니라, 인증·인가·CORS·CSRF 등의 Filter가 정해진 순서로 협력하는 구조이다.

## 3. JWT 인증과 CORS·CSRF

### JWT 인증 흐름

JWT는 사용자의 인증 정보를 전달하는 토큰 형식이다. 일반적인 서명 JWT는 `Header.Payload.Signature`로 구성된다.

Payload는 암호화된 비밀 공간이 아니므로 비밀번호와 같은 민감 정보를 넣으면 안 된다.

|Claim|의미|
|---|---|
|`sub`|토큰의 주체 또는 사용자 식별자|
|`exp`|토큰 만료 시각|
|`nbf`|토큰 사용 가능 시작 시각|
|`iss`|토큰 발급자|
|`aud`|토큰 수신 대상|
|`jti`|토큰 고유 식별자|

토큰 문자열을 파싱하는 데 성공한 것과 안전한 토큰으로 검증한 것은 다르다. 서명, 만료 시각, 발급자, 수신 대상 등 서비스에 필요한 조건을 확인해야 한다.

```text
HTTP 요청 수신
    ↓
Authorization 헤더 확인
    ↓
Bearer Token 추출
    ↓
서명 · 만료 · 발급자 · 수신 대상 검증
    ↓
사용자 식별자와 권한 추출
    ↓
Authentication 생성
    ↓
SecurityContext에 저장
    ↓
다음 Security Filter 실행
    ↓
인가 처리
```

### JWT Filter에서 주의할 예외 범위

토큰 검증을 위한 `try-catch` 안에 `filterChain.doFilter()`까지 포함한 뒤 모든 예외를 401로 바꾸면 Controller나 Service에서 발생한 DB 오류도 인증 실패로 처리될 수 있다.

JWT 파싱·검증 과정에서 발생한 오류와 다음 체인에서 발생한 업무 오류의 범위를 분리해야 한다.

### Session과 JWT 비교

|구분|Session|JWT|
|---|---|---|
|인증 상태|서버가 세션 상태 보관|토큰에 인증 정보를 담아 요청마다 전달|
|클라이언트 전달 값|주로 Session ID|Access Token|
|서버 확장|공유 세션 저장소 등을 고려|서명 검증만으로 기본 확인 가능|
|즉시 무효화|서버 세션 삭제 가능|폐기 목록 등 별도 상태 관리 필요|
|Redis 활용|여러 서버의 공유 세션|Refresh Token·폐기 목록 관리|

JWT 기반 애플리케이션도 요청을 처리하는 동안에는 `SecurityContext`가 필요하다. Redis에서 토큰 상태를 확인한다면 서버 측 상태도 존재하므로 Stateless를 “서버가 어떤 상태도 저장하지 않는다”는 의미로 해석하면 안 된다.

### CORS

CORS는 브라우저가 다른 Origin의 응답에 접근할 수 있는지 통제하는 정책이다. Origin은 `scheme`, `host`, `port`의 조합이다.

`Authorization` 헤더를 사용하는 교차 출처 요청은 브라우저가 실제 요청 전에 `OPTIONS` 프리플라이트를 보낼 수 있다.

```text
브라우저
    ↓ OPTIONS 프리플라이트
CORS 허용 여부 확인
    ↓ 허용
실제 요청 전송
    ↓
Security Filter Chain
```

프리플라이트에는 실제 사용자의 인증 정보가 포함되지 않을 수 있으므로 CORS 처리가 인증 검사보다 먼저 이루어져야 한다.

`OPTIONS` 요청을 `permitAll()`로 설정하는 것만으로 필요한 CORS 응답 헤더가 자동 완성되는 것은 아니다. 허용 Origin, Method, Header를 별도로 설정해야 한다.

### CSRF

CSRF는 브라우저가 쿠키와 같은 인증 정보를 자동으로 전송한다는 특성을 악용해 사용자가 의도하지 않은 상태 변경 요청을 보내는 공격이다.

JWT를 사용한다는 사실만으로 CSRF 위험이 사라지는 것은 아니다. JWT 또는 Refresh Token을 쿠키로 전달한다면 브라우저가 자동 전송할 수 있으므로 CSRF 보호를 검토해야 한다.

> CORS는 브라우저의 교차 출처 응답 접근 정책이고, CSRF는 자동 전송되는 인증 정보를 악용한 요청 위조 공격이다.

## 4. Redis 기본 사용과 Spring Data Redis

### Redis의 역할

Redis는 메모리를 중심으로 동작하는 자료구조 저장소이다. 빠른 조회와 만료 기능이 필요한 데이터에 주로 활용한다.

|자료구조|활용 예시|
|---|---|
|String|캐시, 인증 코드, 토큰 상태|
|Hash|객체의 여러 필드|
|List|순서가 있는 데이터|
|Set|중복 없는 구성원 목록|
|Sorted Set|점수를 기준으로 정렬되는 순위|

Redis가 빠르다는 이유로 모든 데이터를 저장하기보다, 원본 데이터와 캐시·임시 상태의 책임을 구분해야 한다.

### 기본 명령어

다음은 Redis 동작을 이해하기 위한 명령어 예시이다.

```bash
PING
SET study:name "taein"
GET study:name
EXISTS study:name
DEL study:name
```

- `PING`: Redis 연결 상태 확인
- `SET`: 값 저장
- `GET`: 값 조회
- `EXISTS`: 키 존재 여부 확인
- `DEL`: 키 삭제

### TTL 설정

```bash
SET auth:code:demo "123456" EX 180
TTL auth:code:demo
PTTL auth:code:demo
```

|결과 또는 옵션|의미|
|---|---|
|`EX`|초 단위 만료 시간 설정|
|`PX`|밀리초 단위 만료 시간 설정|
|`TTL`|남은 시간을 초 단위로 조회|
|`PTTL`|남은 시간을 밀리초 단위로 조회|
|`TTL -1`|키는 존재하지만 만료 시간이 없음|
|`TTL -2`|키가 존재하지 않음|

일반적인 `GET`은 키의 TTL을 연장하지 않는다. 기존 키를 만료 옵션 없이 다시 `SET`하면 기존 TTL이 제거될 수 있으므로 새로운 만료 시간이나 `KEEPTTL` 적용 여부를 확인해야 한다.

### 조건부 저장

```bash
SET study:once "done" NX EX 60
```

`NX`는 키가 존재하지 않을 때만 값을 저장한다. `SET`과 `EXPIRE`를 별도로 호출하면 두 명령 사이에서 장애가 발생해 만료 시간이 없는 키가 남을 수 있다.

`SET NX EX`는 조건부 저장과 만료 설정을 하나의 명령으로 처리한다. 다만 이 명령 하나의 원자성이 Redis·DB·외부 API를 포함한 전체 업무의 원자성을 의미하지는 않는다.

### Spring Boot 연결

```yaml
spring:
  data:
    redis:
      host: localhost
      port: 6379
      connect-timeout: 2s
      timeout: 2s
```

애플리케이션과 Redis가 서로 다른 컨테이너에서 실행된다면 `localhost`는 Redis가 아니라 현재 애플리케이션 컨테이너를 가리킨다. 같은 Docker Network에 연결한 뒤 Redis의 서비스 이름 등을 사용해야 한다.

### `StringRedisTemplate` 예제

다음 코드는 문자열 값을 저장·조회·삭제하는 설명용 예제이다.

```java
@Service
public class StudyRedisService {

    private final StringRedisTemplate redisTemplate;

    public StudyRedisService(StringRedisTemplate redisTemplate) {
        this.redisTemplate = redisTemplate;
    }

    public void save(String id, String value) {
        redisTemplate.opsForValue()
                .set("study:" + id, value, Duration.ofMinutes(3));
    }

    public String find(String id) {
        return redisTemplate.opsForValue().get("study:" + id);
    }

    public boolean saveIfAbsent(String id, String value) {
        return Boolean.TRUE.equals(
                redisTemplate.opsForValue().setIfAbsent(
                        "study:" + id,
                        value,
                        Duration.ofSeconds(60)
                )
        );
    }

    public void delete(String id) {
        redisTemplate.delete("study:" + id);
    }
}
```

만료됐거나 존재하지 않는 키를 조회하면 `null`이 반환될 수 있다. Redis는 외부 저장소이므로 캐시 미스와 Redis 연결 실패도 구분해서 처리해야 한다.

### Cache Aside 흐름

```text
조회 요청
    ↓
Redis 캐시 조회
    ├─ Cache Hit → 캐시 데이터 반환
    └─ Cache Miss
            ↓
        DB 조회
            ↓
        Redis에 TTL과 함께 저장
            ↓
        데이터 반환
```

DB 데이터를 변경하고 기존 캐시를 그대로 두면 이전 값이 반환될 수 있다. 일반적으로 DB 커밋 이후 관련 캐시를 삭제하거나 갱신하지만, 읽기와 쓰기가 동시에 발생하면 이전 값을 읽은 요청이 캐시에 다시 저장하는 경쟁도 고려해야 한다.

> TTL은 데이터의 보관 시간을 제한하지만, 데이터 최신성이나 동시성 문제까지 자동으로 해결하지는 않는다.

## 5. Redis를 이용한 인증 상태 관리

### Refresh Token 저장

Refresh Token은 새로운 Access Token을 발급받을 때 사용한다. 서버에서 토큰 상태를 제어하려면 Redis에 Refresh Token 또는 검증 가능한 해시를 저장할 수 있다.

```text
Refresh Token 전달
    ↓
토큰 형식과 유효기간 검증
    ↓
Redis에 저장된 상태와 비교
    ↓
일치 여부 확인
    ├─ 불일치 → 재발급 거부
    └─ 일치 → 새로운 Access Token 발급
                    ↓
              회전 정책에 따라
              Refresh Token 교체
```

키에는 사용자뿐 아니라 기기 또는 로그인 세션 식별자를 포함할 수 있다.

```text
auth:refresh:{userId}:{deviceId}
```

사용자 ID만 사용하면 다른 기기에서 로그인했을 때 기존 Refresh Token이 덮어써질 수 있다. 키 구조는 서비스의 동시 로그인 정책에 맞춰야 한다.

### Access Token 폐기 목록

서명된 JWT는 클라이언트에서 삭제해도 이미 발급된 토큰 자체가 즉시 무효화되지는 않는다.

로그아웃 직후부터 Access Token을 거부해야 한다면 토큰의 `jti`를 폐기 목록에 저장하고, 남은 유효기간만큼 TTL을 설정할 수 있다.

```text
auth:revoked:{jti} = 1
TTL = Access Token 만료 시각 - 현재 시각
```

Refresh Token만 삭제하면 추가 재발급은 막을 수 있지만 기존 Access Token은 만료 전까지 사용할 수 있다.

### 인증 데이터 사용 시 주의점

- 토큰 원문이나 비밀번호를 Redis 키에 포함하지 않는다.
- Refresh Token은 원문보다 해시 또는 검증 가능한 식별 정보로 관리하는 방식을 검토한다.
- 동일한 Refresh Token으로 재발급 요청이 동시에 들어오면 비교와 교체를 원자적으로 처리해야 한다.
- 폐기 목록이 메모리 부족으로 먼저 제거되면 무효화한 토큰이 다시 허용될 수 있다.
- Redis 장애를 토큰 위조와 같은 401 오류로 처리하지 않고 의존 서비스 장애와 구분해야 한다.

### 재실행 방지·멱등성·분산 락 비교

|방식|해결 대상|해결하지 못하는 범위|
|---|---|---|
|`OncePerRequestFilter`|동일 요청 처리 중 Filter 내부 로직의 재실행|클라이언트가 보낸 별개의 중복 요청|
|`SET NX EX`|Redis 키가 없을 때만 값 저장|DB와 외부 API를 포함한 전체 업무 원자성|
|멱등키|같은 요청의 재전송에 동일한 결과 제공|서로 다른 자원에 대한 동시 수정|
|분산 락|여러 서버의 동일 자원 동시 접근 조정|데이터베이스 제약과 업무 규칙 전체|
|DB 고유 제약|최종 데이터의 중복 저장 차단|외부 API의 중복 호출과 응답 복원|

분산 락을 Redis로 구현할 때는 고유한 소유자 값을 함께 저장해야 한다.

```text
SET lock:resource:42 "unique-owner-token" NX PX 30000
```

락을 해제할 때 단순히 `DEL`하면 만료 후 다른 요청이 획득한 락을 삭제할 수 있다. 저장된 값이 자신의 소유자 값과 같은지 확인하고 원자적으로 삭제해야 한다.

> Filter 실행 횟수를 제한하는 것과 주문·결제 같은 업무 요청의 중복 처리를 막는 것은 서로 다른 문제이다.

# 🐛 문제 해결

## 문제

Spring Filter가 요청당 한 번만 실행되도록 지원하는 클래스가 `GenericFilterBean`인지 명확하지 않았다.

### 원인

두 클래스 모두 Spring에서 Filter 구현을 돕는 기반 클래스이지만 역할이 다르며, `OncePerRequestFilter`의 “한 번 실행” 범위도 단순히 HTTP 요청 전체의 한 번으로 이해하기 쉬웠다.

### 해결

- `GenericFilterBean`은 Spring 환경에서 Filter를 편리하게 구현하도록 지원하지만 중복 실행 제어 기능은 제공하지 않는다는 점을 확인했다.
- `OncePerRequestFilter`는 `GenericFilterBean`을 상속하고 요청 속성을 이용해 `doFilterInternal()`의 재실행을 제어한다는 점을 확인했다.
- `ASYNC`와 `ERROR` 디스패치는 관련 메서드와 Filter 등록 설정에 따라 별도로 실행될 수 있음을 구분했다.
- 실제 중복 실행을 판단할 때는 프리플라이트, 다른 URI 요청, 재디스패치, Filter 이중 등록을 함께 확인해야 한다는 기준을 정리했다.

### 배운 점

> `GenericFilterBean`은 Filter 구현을 편리하게 만드는 기반 클래스이고, `OncePerRequestFilter`는 정해진 디스패치 범위에서 Filter 내부 로직의 재실행을 제어하는 클래스이다.

- Filter에서 헤더를 읽는 행위만으로 인증이 끝나는 것이 아니라, 토큰을 검증하고 `Authentication`을 `SecurityContext`에 저장해야 Spring Security가 인증된 요청으로 판단한다.
- `permitAll()`은 인가 규칙이므로 앞에 배치된 JWT Filter의 실행 자체를 생략하지 않는다.

## Docker Image와 Container

## ECR Push·Pull 흐름

```text
IAM 권한 확인
    ↓
AWS 인증 정보 확인
    ↓
Credential Helper 또는 Docker 인증
    ↓
로컬 Image에 ECR 주소로 Tag 지정
    ↓
ECR Push
    ↓
다른 환경에서 ECR Pull
```

IAM 권한은 ECR API 호출 가능 여부를 결정하고, Credential Helper는 Docker가 ECR에 접근할 때 필요한 인증 정보를 제공한다. Image Tag에는 ECR Registry 주소, Repository 이름, 버전이 정확하게 포함되어야 한다.

## 1. Entity와 DTO 변환

### 개념

Entity는 테이블 그 자체가 아니라, DB 테이블의 데이터와 매핑되어 JPA가 관리하는 객체다. DTO는 계층 간에 필요한 데이터만 전달하는 객체이며 JPA의 관리 대상이 아니다.

|구분|Entity|DTO|
|---|---|---|
|주요 역할|DB 데이터와 객체의 매핑|요청·응답 데이터 전달|
|JPA 관리|영속성 컨텍스트가 관리함|JPA가 관리하지 않음|
|변경 영향|트랜잭션 안에서 DB 변경으로 이어질 수 있음|객체 값만 변경됨|
|연관관계|다른 Entity와 연관관계를 가질 수 있음|필요한 데이터만 평면적으로 구성 가능|
|외부 노출|직접 노출하지 않는 것이 안전함|API 요청·응답에 사용함|

Entity를 API 응답으로 직접 반환하면 불필요한 필드가 노출되거나 양방향 연관관계로 순환 참조가 발생할 수 있다. 지연 로딩된 연관관계가 직렬화되는 과정에서 추가 쿼리나 예외가 발생할 가능성도 있다.

### 팩토리 메서드 패턴

DTO 내부에 `from()`과 같은 정적 팩토리 메서드를 두면 Entity를 DTO로 변환하는 규칙을 한곳에서 관리할 수 있다.

다음은 패턴을 설명하기 위한 예제다.

```java
@Getter
@AllArgsConstructor(access = AccessLevel.PRIVATE)
public class UserDTO {

    private final Long id;
    private final String name;
    private final String email;

    public static UserDTO from(UserEntity entity) {
        return new UserDTO(
            entity.getId(),
            entity.getName(),
            entity.getEmail()
        );
    }
}
```

호출하는 쪽에서는 생성자에 값을 직접 나열하지 않고 변환 의도가 드러나는 메서드를 사용한다.

```java
UserEntity userEntity = userRepository.findById(userId)
    .orElseThrow();

UserDTO userDTO = UserDTO.from(userEntity);
```

### 변환 흐름

```text
DB 조회 결과
    ↓
JPA가 Entity 생성 및 관리
    ↓
UserDTO.from(userEntity)
    ↓
응답에 필요한 필드만 복사
    ↓
UserDTO 반환
    ↓
JSON 응답으로 직렬화
```

### 주의점

- DTO가 필요로 하는 지연 로딩 연관관계는 영속성 컨텍스트가 열려 있을 때 조회해야 한다.
- DTO 변환 과정에서 연관 Entity를 반복 조회하면 N+1 문제가 발생할 수 있다.
- Entity에 비밀번호나 내부 상태값이 있어도 응답 DTO에 포함하지 않으면 외부 노출을 막을 수 있다.
- 변환 규칙을 Controller마다 작성하지 않고 DTO의 팩토리 메서드로 모으면 중복을 줄일 수 있다.

### 핵심 포인트

> Entity는 영속성 관리를 위한 객체이고 DTO는 데이터 전달을 위한 객체다. API 응답에는 Entity 대신 필요한 값만 담은 DTO를 사용한다.

## 2. JPA 외부 DB 연동과 CRUD JUnit 테스트

### 외부 DB 연동

Spring Boot가 외부 DB를 사용하려면 DB 드라이버와 접속 정보가 필요하다. 설정된 정보를 바탕으로 `DataSource`가 연결을 생성하고 JPA가 이를 이용해 SQL을 실행한다.

```yaml
spring:
  datasource:
    url: ${DB_URL}
    username: ${DB_USERNAME}
    password: ${DB_PASSWORD}

  jpa:
    show-sql: true
```

실제 URL 형식과 JDBC 드라이버는 사용하는 DB 종류에 맞아야 한다.

### 연결 흐름

```text
Spring Boot 실행
    ↓
DB 접속 설정 확인
    ↓
DataSource 생성
    ↓
JPA EntityManagerFactory 생성
    ↓
Repository 메서드 호출
    ↓
Hibernate가 SQL 생성
    ↓
외부 DB에서 SQL 실행
```

### JPA CRUD 동작

|작업|Repository 메서드|핵심 동작|
|---|---|---|
|Create|`save()`|새로운 Entity를 영속화하고 INSERT를 실행한다.|
|Read|`findById()`|식별자로 Entity를 조회하고 `Optional`로 반환한다.|
|Update|변경 감지|관리 중인 Entity의 값이 바뀌면 flush 시 UPDATE가 실행된다.|
|Delete|`delete()`|Entity를 삭제 상태로 만들고 flush 시 DELETE가 실행된다.|

JPA의 수정은 반드시 별도의 UPDATE 메서드를 호출해야 하는 방식이 아니다. 트랜잭션 안에서 조회한 Entity는 영속성 컨텍스트가 관리하므로 값을 변경하면 변경 감지가 동작한다.

### CRUD 테스트

다음은 전체 흐름을 설명하기 위한 예제다.

```java
@SpringBootTest
@Transactional
class UserRepositoryTest {

    @Autowired
    private UserRepository userRepository;

    @Test
    void crud() {
        // Create
        UserEntity saved =
            userRepository.save(new UserEntity("태인", "user@example.com"));

        Long userId = saved.getId();

        // Read
        UserEntity found = userRepository.findById(userId)
            .orElseThrow();

        assertEquals("태인", found.getName());

        // Update
        found.changeName("엄태인");
        userRepository.flush();

        assertEquals("엄태인", found.getName());

        // Delete
        userRepository.delete(found);
        userRepository.flush();

        assertFalse(userRepository.existsById(userId));
    }
}
```

### 테스트에서 확인할 부분

- `save()` 이후 식별자가 정상적으로 생성되는지 확인한다.
- `findById()`의 반환값이 `Optional`이라는 점을 확인한다.
- 관리 상태의 Entity를 변경했을 때 변경 감지가 동작하는지 확인한다.
- `delete()` 이후 데이터가 조회되지 않는지 확인한다.
- `flush()`를 사용하면 트랜잭션 종료 전에도 SQL 실행 결과를 확인할 수 있다.

`@Transactional`이 적용된 테스트는 일반적으로 테스트 종료 후 롤백되므로 외부 DB에 테스트 데이터가 남는 것을 방지할 수 있다. 다만 테스트 설정과 트랜잭션 적용 여부를 반드시 확인해야 한다.

### 외부 DB 테스트 주의점

- 운영 DB가 아닌 테스트 전용 DB나 별도 스키마를 사용한다.
- 테스트에서 실제로 어떤 DB에 연결됐는지 접속 URL을 확인한다.
- `@DataJpaTest`는 설정에 따라 내장 DB로 교체될 수 있으므로 외부 DB 테스트 목적이라면 DataSource 교체 여부를 확인한다.
- SQL 실행 시점은 메서드 호출 시점과 항상 같지 않으며 flush 또는 commit 시 실행될 수 있다.

### 핵심 포인트

> JPA CRUD 테스트는 메서드 호출 여부만 보는 것이 아니라, 영속성 컨텍스트의 상태 변화와 실제 SQL 실행 결과까지 확인해야 한다.

## 3. JPA 연관관계 옵션

Entity 사이에 연관관계가 있으면 부모의 작업을 자식에게 전파할지, 관계에서 제외된 자식을 삭제할지, 연관 데이터를 언제 조회할지를 결정해야 한다.

### 옵션 비교

|옵션|결정하는 것|대표 동작|
|---|---|---|
|`cascade`|Entity 작업의 전파 범위|부모 저장·삭제 시 자식도 함께 저장·삭제|
|`orphanRemoval`|관계에서 제거된 자식의 삭제 여부|부모 컬렉션에서 빠진 자식을 DB에서 삭제|
|`fetch`|연관 Entity의 조회 시점|즉시 로딩 또는 지연 로딩|

### cascade

`cascade`는 부모 Entity에 수행한 영속성 작업을 연관된 자식 Entity에도 전파한다.

|종류|전파되는 작업|
|---|---|
|`PERSIST`|부모를 저장할 때 자식도 저장|
|`MERGE`|부모를 병합할 때 자식도 병합|
|`REMOVE`|부모를 삭제할 때 자식도 삭제|
|`REFRESH`|부모를 새로 읽을 때 자식도 새로 읽음|
|`DETACH`|부모를 준영속 상태로 만들 때 자식도 함께 처리|
|`ALL`|모든 cascade 작업 적용|

`CascadeType.ALL`은 편리하지만 모든 연관관계에 무조건 적용하면 안 된다. 자식의 생명주기를 부모가 완전히 소유하는 관계인지 먼저 판단해야 한다.

### orphanRemoval

`orphanRemoval = true`는 부모와의 연관관계에서 제거된 자식 Entity를 삭제한다.

```text
부모 Entity가 자식 컬렉션을 관리
    ↓
컬렉션에서 자식 Entity 제거
    ↓
영속성 컨텍스트가 관계 변경 감지
    ↓ flush
자식 Entity에 DELETE 실행
```

`CascadeType.REMOVE`와 `orphanRemoval`은 삭제가 시작되는 조건이 다르다.

|구분|`CascadeType.REMOVE`|`orphanRemoval = true`|
|---|---|---|
|주요 시작 조건|부모 Entity 자체를 삭제|부모와 자식의 연관관계를 제거|
|주요 목적|부모 삭제를 자식에게 전파|부모에게서 떨어진 고아 객체 삭제|
|컬렉션에서 자식만 제거|자식 삭제를 보장하지 않음|자식 Entity를 삭제함|

### fetch

`fetch`는 연관된 Entity를 언제 조회할지 결정한다.

|방식|의미|주의점|
|---|---|---|
|`FetchType.EAGER`|연관 Entity를 즉시 사용할 수 있게 조회|불필요한 조회와 추가 SQL이 발생할 수 있음|
|`FetchType.LAZY`|연관 Entity를 실제로 사용할 때 조회|영속성 컨텍스트 밖에서 접근하면 예외가 발생할 수 있음|

JPA 연관관계의 기본 로딩 방식은 다음과 같다.

|연관관계|기본 FetchType|
|---|---|
|`@OneToOne`|`EAGER`|
|`@ManyToOne`|`EAGER`|
|`@OneToMany`|`LAZY`|
|`@ManyToMany`|`LAZY`|

EAGER라고 해서 반드시 하나의 JOIN SQL로 조회되는 것은 아니다. JPA 구현체의 조회 방식에 따라 추가 SQL이 실행될 수 있다.

### 연관관계 설정 예제

다음은 각 옵션의 관계를 설명하기 위한 예제다.

```java
@Entity
public class UserEntity {

    @OneToMany(
        mappedBy = "user",
        cascade = CascadeType.ALL,
        orphanRemoval = true,
        fetch = FetchType.LAZY
    )
    private List<PostEntity> posts = new ArrayList<>();

    public void addPost(PostEntity post) {
        posts.add(post);
        post.changeUser(this);
    }

    public void removePost(PostEntity post) {
        posts.remove(post);
        post.changeUser(null);
    }
}
```

이 설정에서는 다음과 같이 동작한다.

```text
UserEntity 저장
    ↓ cascade
연관된 PostEntity도 저장

UserEntity에서 PostEntity 제거
    ↓ orphanRemoval
제거된 PostEntity 삭제

UserEntity 조회
    ↓ fetch = LAZY
posts를 실제로 사용할 때 조회
```

### 주의점

- `cascade`는 영속성 작업을 전파할 뿐 연관관계의 주인을 자동으로 설정하지 않는다.
- 양방향 연관관계에서는 편의 메서드로 양쪽 객체의 관계를 함께 맞춰야 한다.
- `orphanRemoval`은 부모가 자식의 생명주기를 책임지는 관계에 적합하다.
- `LAZY`로 설정해도 반복 접근 방식에 따라 N+1 쿼리가 발생할 수 있다.
- DTO 팩토리 메서드에서 지연 로딩 컬렉션에 접근하면 추가 SQL이 실행될 수 있다.

### 핵심 포인트

> `cascade`는 작업을 전파하고, `orphanRemoval`은 관계에서 제외된 자식을 삭제하며, `fetch`는 연관 데이터를 가져오는 시점을 결정한다.

## 4. User Controller Validation

### 개념

Validation은 클라이언트가 보낸 요청값이 애플리케이션이 요구하는 형식과 조건을 만족하는지 검사하는 과정이다.

Entity에 잘못된 데이터가 전달된 뒤 검증하기보다 요청 DTO에서 먼저 검증하면 Controller와 Service가 유효한 입력을 기준으로 동작할 수 있다.

### 주요 검증 애너테이션

|애너테이션|검사 대상|검증 기준|
|---|---|---|
|`@NotNull`|모든 참조 타입|`null`만 허용하지 않음|
|`@NotEmpty`|문자열·컬렉션·배열·Map|`null`과 빈 값을 허용하지 않음|
|`@NotBlank`|문자열|`null`, 빈 문자열, 공백 문자열을 허용하지 않음|
|`@Email`|문자열|이메일 형식인지 검사|
|`@Size`|문자열·컬렉션 등|길이나 크기가 지정 범위인지 검사|

문자열의 실제 내용이 필요한 경우에는 단순히 `null`만 막는 `@NotNull`보다 `@NotBlank`가 적합하다.

### 요청 DTO 예제

다음은 Validation 적용 방식을 설명하기 위한 예제다.

```java
public class UserCreateRequest {

    @NotBlank(message = "이름은 필수입니다.")
    private String name;

    @NotBlank(message = "이메일은 필수입니다.")
    @Email(message = "이메일 형식이 올바르지 않습니다.")
    private String email;

    // 생성자와 Getter 생략
}
```

Controller의 `@RequestBody` 앞에 `@Valid`를 적용해야 요청 DTO에 선언한 검증 조건이 실행된다.

```java
@RestController
@RequestMapping("/users")
public class UserController {

    @PostMapping
    public UserDTO createUser(
        @Valid @RequestBody UserCreateRequest request
    ) {
        return userService.createUser(request);
    }
}
```

### 동작 흐름

```text
클라이언트가 JSON 요청 전송
    ↓
요청 JSON을 UserCreateRequest로 변환
    ↓
@Valid가 DTO의 검증 조건 실행
    ↓
검증 성공
    └─ Controller 메서드 실행
    ↓
검증 실패
    └─ MethodArgumentNotValidException 발생
       ↓
       잘못된 요청 응답 처리
```

### Validation의 범위

Validation은 값의 형식과 기본 조건을 검사한다. 이메일 중복 여부처럼 DB 조회가 필요한 규칙은 Service의 비즈니스 검증으로 처리해야 한다.

|검증 종류|확인 대상|예시|
|---|---|---|
|입력값 Validation|요청 형식과 값의 범위|필수값, 이메일 형식, 문자열 길이|
|비즈니스 검증|도메인 규칙과 현재 데이터|이메일 중복, 상태 변경 가능 여부|
|인증|요청한 사용자의 신원|유효한 로그인 사용자 여부|
|인가|해당 기능에 대한 권한|관리자 기능 접근 가능 여부|

### 핵심 포인트

> 요청 DTO의 제약 조건은 `@Valid`가 있어야 실행된다. 입력값 검증과 DB가 필요한 비즈니스 검증은 역할이 다르다.

---

## 5. 인증과 인가

### 개념 비교

|구분|인증(Authentication)|인가(Authorization)|
|---|---|---|
|핵심 질문|누구인가?|무엇을 할 수 있는가?|
|확인 대상|사용자의 신원|사용자의 역할과 권한|
|대표 정보|아이디·비밀번호·토큰|사용자 역할·권한 목록|
|처리 순서|먼저 수행|인증 이후 수행|
|일반적인 실패 응답|`401 Unauthorized`|`403 Forbidden`|

인증되지 않은 사용자는 누구인지 확인되지 않았기 때문에 권한을 판단할 수 없다. 따라서 일반적으로 인증이 먼저 수행되고, 인증된 사용자 정보를 기준으로 인가가 진행된다.

### 요청 처리 흐름

Spring Security를 사용하는 일반적인 요청 흐름은 다음과 같다.

```text
클라이언트 요청
    ↓
인증 정보 확인
    ↓
인증 성공
    ↓
인증된 사용자 정보 생성
    ↓
요청한 기능의 권한 확인
    ↓
인가 성공
    ↓
Controller 요청 전달
```

실패 흐름은 다음과 같이 구분한다.

```text
유효한 인증 정보가 없음
    ↓
401 Unauthorized

인증은 성공했지만 필요한 권한이 없음
    ↓
403 Forbidden
```

### Validation과의 차이

- Validation은 요청 데이터의 형식과 값이 올바른지 검사한다.
- 인증은 요청을 보낸 사용자가 누구인지 확인한다.
- 인가는 해당 사용자가 요청한 기능을 실행할 수 있는지 확인한다.

즉, 요청 데이터가 올바르더라도 인증이나 인가에 실패하면 기능을 실행할 수 없다. 반대로 권한이 있는 사용자라도 요청 데이터가 검증 조건을 통과하지 못하면 Controller의 정상 로직을 실행할 수 없다.

### 핵심 포인트

> 인증은 사용자의 신원을 확인하는 과정이고, 인가는 인증된 사용자가 가진 접근 권한을 확인하는 과정이다.

# 🛠️ 실습 / 구현

## 구현한 것

- Entity를 DTO로 변환하는 정적 팩토리 메서드를 작성했다.
- 외부 DB 연결 설정을 적용하고 JPA Repository의 CRUD 동작을 테스트했다.
- JUnit 테스트를 통해 등록·조회·수정·삭제 결과를 확인했다.
- 연관관계에 `cascade`, `orphanRemoval`, `fetch` 속성을 적용하고 동작 차이를 확인했다.
- User 요청 DTO에 검증 조건을 선언하고 Controller에 Validation을 적용했다.
- 정상 요청과 검증 실패 요청의 처리 흐름을 비교했다.

## 실행 흐름

```text
외부 DB 연결 확인
    ↓
Repository로 Entity 저장
    ↓
식별자를 이용해 Entity 조회
    ↓
Entity 값을 변경하고 변경 감지 확인
    ↓
Entity 삭제 결과 확인
    ↓
연관관계 옵션에 따른 데이터 변화 확인
    ↓
Controller 요청 DTO Validation 확인
    ↓
Entity를 응답 DTO로 변환
```

## 확인한 결과

- Entity와 DTO를 분리하면 DB 모델과 API 응답 구조를 독립적으로 관리할 수 있다.
- CRUD 테스트에서는 Repository 반환값뿐 아니라 flush 이후의 DB 상태도 확인해야 한다.
- 부모와 자식의 생명주기에 따라 cascade와 orphanRemoval의 적용 여부를 결정해야 한다.
- fetch 설정은 연관 데이터의 SQL 실행 시점과 성능에 직접 영향을 준다.
- `@Valid`를 적용하면 잘못된 요청을 비즈니스 로직 실행 전에 차단할 수 있다.
- Validation, 인증, 인가는 모두 요청을 검사하지만 각각 값·신원·권한이라는 서로 다른 대상을 확인한다.

# 🧠 오늘 이해한 핵심

- Entity는 DB와 매핑되어 JPA가 관리하는 객체이고, DTO는 요청과 응답에 필요한 데이터만 전달하는 객체다.
- JPA CRUD는 영속성 컨텍스트와 트랜잭션을 기반으로 동작하며, 수정은 관리 상태 Entity의 변경 감지를 통해 처리할 수 있다.
- `cascade`, `orphanRemoval`, `fetch`는 각각 작업 전파, 고아 객체 삭제, 조회 시점을 담당하므로 같은 옵션으로 보면 안 된다.
- 요청 처리에서는 인증으로 사용자를 확인하고 인가로 권한을 검사한 뒤, Validation을 통과한 데이터로 비즈니스 로직을 수행한다.

# 🔍 복습할 부분

- `CascadeType.REMOVE`와 `orphanRemoval = true`가 각각 어떤 조건에서 DELETE를 발생시키는지 다시 비교한다.
- `EAGER`와 `LAZY`의 SQL 실행 시점, 영속성 컨텍스트 범위, N+1 발생 가능성을 함께 확인한다.
- JPA CRUD 테스트에서 `save()`, 변경 감지, `flush()`, 트랜잭션 롤백이 어떤 순서로 동작하는지 다시 따라간다.
- 입력값 Validation과 비즈니스 검증, 인증, 인가가 각각 무엇을 검사하는지 요청 흐름을 기준으로 복습한다.

## 1. Filter·Interceptor·AOP의 실행 위치와 역할

### 개념

Filter, Interceptor, AOP는 모두 여러 곳에서 반복되는 공통 기능을 한곳에서 처리하기 위한 방법이다. 하지만 기준이 다르다.

- Filter는 HTTP 요청과 응답을 기준으로 동작한다.
- Interceptor는 Spring MVC의 Handler, 즉 Controller 실행을 기준으로 동작한다.
- AOP는 Spring Bean의 메서드 호출을 기준으로 동작한다.

### 비교

|구분|Filter|Interceptor|AOP|
|---|---|---|---|
|기준|Servlet HTTP 요청·응답|Spring MVC Handler 실행|Spring Bean 메서드 호출|
|실행 위치|DispatcherServlet 앞·뒤|DispatcherServlet 내부, Controller 전후|프록시가 감싼 메서드 전후|
|대표 메서드|doFilter()|preHandle(), postHandle(), afterCompletion()|@Before, @Around, @After|
|알 수 있는 정보|URL, Method, Header, Cookie|선택된 Controller와 Handler|대상 Bean과 메서드 실행|
|적합한 기능|JWT, CORS, 전역 요청 처리|Controller 로깅, 실행 시간 측정|트랜잭션, 재시도, 공통 서비스 로직|
|오늘의 적용|JwtFilter|Controller 요청 흐름 보조|Service 공통 처리 가능|

### 동작 흐름

```text
클라이언트 요청
    ↓
Servlet Filter
    ↓
DispatcherServlet
    ↓
HandlerInterceptor.preHandle()
    ↓
Controller
    ↓
Service Bean 호출
    ↓
AOP 프록시의 공통 로직
    ↓
Repository
    ↓
응답 반환
    ↓
Interceptor.postHandle() · afterCompletion()
    ↓
Filter 후처리
```

Filter는 DispatcherServlet보다 앞에서 실행되기 때문에 Controller가 선택되기 전에도 요청을 차단하거나 통과시킬 수 있다. 반면 Interceptor는 Spring MVC가 어떤 Controller를 실행할지 결정한 뒤 동작하므로 Controller 중심의 공통 처리에 적합하다.

AOP는 HTTP 요청이 없어도 Spring Bean 메서드 호출에 적용할 수 있다. 예를 들어 Service 메서드의 실행 시간 측정, 트랜잭션 처리, 재시도 로직에 적합하다.

### 핵심 코드

아래는 각 계층의 대표적인 실행 지점을 보여주는 설명용 예시다.

```java
// Filter: Servlet 요청 앞단
public void doFilter(
        ServletRequest request,
        ServletResponse response,
        FilterChain chain) throws IOException, ServletException {
    // 요청 전 처리
    chain.doFilter(request, response);
    // 응답 후 처리
}

// Interceptor: Controller 실행 전후
public boolean preHandle(
        HttpServletRequest request,
        HttpServletResponse response,
        Object handler) {
    return true;
}

// AOP: Spring Bean 메서드 전후
@Around("execution(* com.example..service..*(..))")
public Object measure(ProceedingJoinPoint joinPoint) throws Throwable {
    long start = System.currentTimeMillis();
    Object result = joinPoint.proceed();
    long elapsed = System.currentTimeMillis() - start;
    return result;
}
```

### 핵심 포인트

> JWT 인증은 요청이 Controller에 도달하기 전에 수행되어야 하므로 Filter, 특히 Spring Security Filter Chain에 두는 것이 자연스럽다.

> Interceptor와 AOP는 둘 다 전후 처리를 할 수 있지만, Interceptor는 MVC Handler 중심이고 AOP는 Spring Bean 메서드 중심이다.

> Spring AOP는 기본적으로 프록시 기반이므로 같은 객체 안에서 this로 자기 메서드를 호출하면 AOP가 적용되지 않을 수 있다.

## 2. JSR 303 기반 DTO 유효성 검증

### 개념

JSR 303은 Java 객체의 값을 애너테이션으로 검증하는 Bean Validation 표준이다. 이후 표준이 발전하면서 현재 Spring Boot 3 이상에서는 jakarta.validation 패키지를 사용한다.

- Spring Boot 2 계열: javax.validation
- Spring Boot 3 이상: jakarta.validation

수업에서 말하는 “JSR 303 유효성 체크”는 DTO에 검증 규칙을 선언하고, Controller에 들어오는 요청을 자동으로 검사하는 흐름을 의미한다.

### 필요한 이유

Controller가 Service를 호출하기 전에 요청의 기본 형식을 걸러내면 잘못된 데이터가 애플리케이션 내부로 깊이 들어가는 것을 막을 수 있다. 다만 DTO Validation은 이메일 중복이나 재고 부족처럼 DB와 현재 상태를 확인해야 하는 비즈니스 규칙까지 대신 처리하지 않는다.

### 주요 애너테이션

|애너테이션|검사 내용|주의점|
|---|---|---|
|@NotNull|null 여부|빈 문자열은 허용할 수 있다.|
|@NotEmpty|null과 빈 값|공백 문자열은 통과할 수 있다.|
|@NotBlank|null, 빈 문자열, 공백 문자열|문자열에 사용한다.|
|@Email|이메일 형식|필수값이면 @NotBlank와 함께 사용한다.|
|@Size|문자열 길이, Collection 크기|숫자 값의 범위 검사에는 @Min, @Max를 사용한다.|
|@Pattern|정규표현식 일치 여부|복잡한 업무 규칙은 Service 검증을 고려한다.|
|@Min, @Max|숫자 최솟값·최댓값|숫자의 값 범위를 검사한다.|

### DTO와 Controller 코드

아래 코드는 오늘 개념을 복습하기 위한 설명용 예시다.

```java
import jakarta.validation.constraints.Email;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;

public record SignInRequest(
        @NotBlank(message = "이메일은 필수입니다.")
        @Email(message = "이메일 형식이 올바르지 않습니다.")
        String email,

        @NotBlank(message = "비밀번호는 필수입니다.")
        @Size(min = 8, max = 64)
        String password
) {
}
```

```java
import jakarta.validation.Valid;

@PostMapping("/auth/sign-in")
public ResponseEntity<TokenResponse> signIn(
        @Valid @RequestBody SignInRequest request) {
    return ResponseEntity.ok(authService.signIn(request));
}
```

### 동작 흐름

```text
HTTP JSON 요청
    ↓
HttpMessageConverter가 JSON을 DTO로 변환
    ↓
@Valid가 DTO 제약 조건 검사
    ├─ 실패: Controller 메서드 본문 실행 전 400 응답
    └─ 성공: Controller 메서드 실행
                ↓
             Service 호출
```

@Valid가 붙은 요청 DTO의 검증이 실패하면 일반적으로 MethodArgumentNotValidException이 발생한다. 여러 Controller에서 같은 형식으로 오류를 반환하려면 RestControllerAdvice와 ExceptionHandler를 사용한다.

### 입력값 검증과 비즈니스 검증 비교

|구분|입력값 Validation|비즈니스 검증|
|---|---|---|
|확인 대상|요청 데이터의 형식과 기본 조건|현재 DB 상태와 업무 규칙|
|예시|이메일 형식, 비밀번호 길이, 필수값|이메일 중복, 재고 부족, 작성자 권한|
|주된 위치|DTO와 Controller 진입 경계|Service와 Domain 로직|
|실패 의미|잘못된 요청|현재 업무 조건에 맞지 않는 요청|

### 핵심 포인트

> @Valid는 DTO의 형식과 기본 조건을 검사하는 도구이지, 사용자가 실제로 로그인할 수 있는지 또는 해당 작업을 해도 되는지까지 판단하는 도구는 아니다.

> @Email만으로 필수 이메일이 보장되는 것은 아니므로 필수 문자열에는 보통 @NotBlank를 함께 사용한다.

## 3. JWT 구조와 Access·Refresh Token

### 개념

JWT(JSON Web Token)는 사용자 인증 정보를 토큰으로 표현하는 방식이다. 일반적인 서명 JWT는 암호화된 값이 아니라 변조 여부를 검증하기 위한 값이므로 Payload에 비밀번호나 Secret 같은 민감정보를 넣으면 안 된다.

### JWT 구조

|구성|역할|
|---|---|
|Header|토큰 타입과 서명 알고리즘 정보|
|Payload|사용자 식별자, 발급·만료 시각, 권한 같은 Claim|
|Signature|Header와 Payload가 서명 후 변조되지 않았는지 검증|

```text
Header.Payload.Signature
```

### 주요 Claim

|Claim|의미|학습 내용과의 연결|
|---|---|---|
|sub|Subject, 토큰의 주체|수업 코드에서는 이메일 또는 사용자 식별자를 넣을 수 있다.|
|iat|Issued At, 발급 시각|토큰이 언제 발급됐는지 나타낸다.|
|exp|Expiration, 만료 시각|만료된 토큰을 더 이상 인증에 사용할 수 없게 한다.|
|jti|JWT ID|Refresh Token 세션 구분이나 폐기에 활용할 수 있다.|
|role|애플리케이션이 정의한 권한 Claim|인증 후 인가에 활용할 수 있다.|

### Access Token과 Refresh Token

|구분|Access Token|Refresh Token|
|---|---|---|
|목적|보호된 API 호출|새 Access Token 발급|
|수명|짧게 설정|비교적 길게 설정|
|사용 위치|일반 API 요청의 Authorization Header|재발급 Endpoint|
|서버 저장|보통 저장하지 않음|Redis 또는 DB에 저장 가능|
|탈취 시 영향|만료 전 API 호출 가능|새 Access Token을 다시 발급받을 수 있음|

### 생성 흐름

```text
사용자 인증 성공
    ↓
사용자 식별자와 필요한 Claim 결정
    ↓
iat와 exp 설정
    ↓
Secret Key로 서명
    ↓
compact()로 최종 JWT 문자열 생성
```

### 핵심 코드

첫 번째 화면에서 확인한 JwtProvider의 생성 방식은 다음과 같은 Builder 흐름이었다. 아래는 화면의 코드를 학습용으로 정리한 것이다.

```java
public String createAccessToken(String email) {
    return Jwts.builder()
            .setSubject(email)
            .setIssuedAt(new Date())
            .setExpiration(
                    new Date(System.currentTimeMillis() + ACCESS_TOKEN_EXPIRY)
            )
            .signWith(getSecretKey())
            .compact();
}
```

- Jwts.builder()로 JWT 생성을 시작한다.
- setSubject(email)로 sub Claim을 설정한다.
- setIssuedAt()으로 발급 시각을 기록한다.
- setExpiration()으로 만료 시각을 설정한다.
- signWith()로 Secret Key를 이용해 서명한다.
- compact()가 Header, Payload, Signature를 조합한 문자열을 반환한다.

JJWT 버전에 따라 setSubject() 대신 subject(), setIssuedAt() 대신 issuedAt()처럼 메서드 이름이 달라질 수 있다. 중요한 것은 메서드 이름보다 Claim 설정 → 서명 → compact라는 순서다.

### 대칭키와 Secret 관리

대칭키 방식에서는 같은 Secret Key로 토큰을 서명하고 검증한다. 구현이 간단하고 빠르지만, 토큰을 검증하는 모든 서버가 Secret을 알고 있어야 한다.

실제 Secret은 코드나 Git에 직접 작성하지 않고 환경변수 또는 Secret Manager에서 주입한다.

```yaml
spring:
  config:
    import: optional:file:.env[.properties]

jwt:
  secret: ${JWT_SECRET}
  access-expiration: ${JWT_ACCESS_EXPIRATION:15m}
  refresh-expiration: ${JWT_REFRESH_EXPIRATION:14d}
```

```text
openssl rand -base64 32
```

주의할 점은 Spring Boot가 프로젝트 루트의 .env 파일을 항상 자동으로 읽는 것은 아니라는 점이다. IDE 실행 설정, Docker Compose, dotenv 라이브러리 또는 명시적인 Config Import가 필요하다.

### 핵심 포인트

> JWT의 Payload는 서명됐다고 해서 암호화되는 것이 아니다. 누구나 읽을 수 있다고 가정하고 민감한 정보를 넣지 않는다.

> Secret Key, Access Token, Refresh Token 원문을 로그에 출력하면 안 된다. 화면의 실행 로그처럼 Secret이 출력되는 구조는 학습 중 확인하더라도 실제 서비스에서는 제거해야 한다.

## 4. 로그인부터 Refresh Token 저장까지

### 로그인 흐름

로그인에서는 DTO 형식 검증이 성공한 뒤 Service가 사용자를 조회하고 비밀번호를 확인한다. 인증에 성공해야 JwtProvider가 토큰을 발급한다.

```text
POST /auth/sign-in
    ↓
SignInRequest DTO 변환
    ↓
@Valid 입력값 검증
    ↓
UserService
    ↓
UserRepository로 사용자 조회
    ↓
PasswordEncoder로 비밀번호 비교
    ↓
JwtProvider.createAccessToken()
    ↓
JwtProvider.createRefreshToken()
    ↓
Refresh Token을 Redis에 저장하고 TTL 설정
    ↓
TokenResponse 반환
```

### Refresh Token을 Redis에 저장하는 이유

Access Token만 사용하면 서버가 토큰 발급 상태를 별도로 저장하지 않는 Stateless 구조를 만들기 쉽다. 하지만 Refresh Token을 Redis에 저장하면 서버가 해당 세션을 통제할 수 있다.

- 로그아웃 시 Refresh Token을 삭제할 수 있다.
- 만료 시간을 Redis TTL로 관리할 수 있다.
- 특정 사용자 또는 기기의 Refresh Token만 폐기할 수 있다.
- 재발급 시 Redis에 존재하는 토큰인지 확인할 수 있다.

Redis Key는 사용자 한 명당 하나로 고정하기보다 여러 기기 로그인을 고려해 사용자 ID, 세션 ID 또는 jti를 함께 사용하는 것을 검토한다.

### Refresh Token 재발급 흐름

```text
Access Token 만료
    ↓
Refresh Token으로 재발급 요청
    ↓
Refresh Token 서명·만료·tokenType 검증
    ↓
Redis에 저장된 세션과 일치하는지 확인
    ↓
새 Access Token 발급
    ↓
필요하면 Refresh Token도 교체(Rotation)
```

Refresh Token을 Access Token처럼 일반 API 호출에 사용하지 못하도록 tokenType Claim 또는 별도 검증 정책을 둘 수 있다.

### 로그아웃의 한계

Redis에서 Refresh Token을 삭제하면 새 Access Token을 재발급받는 것은 막을 수 있다. 하지만 이미 발급된 Access Token은 별도 Denylist나 Token Version 정책이 없다면 만료 시각까지 유효할 수 있다.

따라서 일반적으로 다음 조합을 고려한다.

- Access Token은 짧은 만료 시간으로 설정한다.
- 로그아웃하면 Redis의 Refresh Token을 삭제한다.
- 즉시 차단이 필요하면 Access Token Denylist 또는 사용자별 Token Version을 추가한다.

### 핵심 포인트

> Refresh Token을 Redis에 저장하는 목적은 단순히 토큰을 보관하는 것이 아니라, 재발급과 로그아웃을 서버가 통제할 수 있게 만드는 것이다.

## 5. CORS, JwtFilter, SecurityContext와 실제 요청 흐름

### CORS Preflight

프론트엔드와 백엔드의 Origin이 다르고 Authorization 같은 헤더를 사용하는 경우 브라우저는 실제 요청 전에 OPTIONS Preflight 요청을 보낼 수 있다.

```http
OPTIONS /blogs/index
Origin: http://localhost:5173
Access-Control-Request-Method: GET
Access-Control-Request-Headers: Authorization
```

Preflight는 실제 API를 실행하는 요청이 아니라 “이 Origin과 Method와 Header를 허용하는가?”를 묻는 요청이다. 이 요청에는 실제 Access Token이 없을 수 있으므로 JwtFilter가 무조건 토큰을 요구하면 실제 GET 요청까지 도달하지 못한다.

### JwtFilter의 역할

JwtFilter는 보호된 요청에서 Authorization Header를 읽고, Bearer Token을 검증한 뒤 인증 객체를 만든다.

```text
Authorization: Bearer {Access Token}
    ↓
Bearer 접두사 제거
    ↓
JWT 형식 확인
    ↓
Signature 검증
    ↓
exp와 tokenType 확인
    ↓
sub에서 사용자 식별자 추출
    ↓
Authentication 생성
    ↓
SecurityContext에 저장
    ↓
다음 Filter와 인가 처리로 전달
```

### 설명용 JwtFilter 핵심 코드

```java
String authorization = request.getHeader(HttpHeaders.AUTHORIZATION);

if (authorization != null && authorization.startsWith("Bearer ")) {
    String token = authorization.substring(7);
    Claims claims = jwtProvider.parseClaims(token);

    String userId = claims.getSubject();

    Authentication authentication =
            new UsernamePasswordAuthenticationToken(
                    userId,
                    null,
                    authorities
            );

    SecurityContext context = SecurityContextHolder.createEmptyContext();
    context.setAuthentication(authentication);
    SecurityContextHolder.setContext(context);
}

filterChain.doFilter(request, response);
```

이 코드는 JWT가 유효하다는 전제에서 인증 객체를 저장하는 구조를 보여주는 설명용 예시다. 실제 구현에서는 만료, 위조, 형식 오류를 예외 처리하고, 토큰이 없는 공개 Endpoint와 Preflight 요청을 어떻게 통과시킬지 Security 설정과 함께 결정해야 한다.

### Authentication과 Authorization

- Authentication은 “이 사용자가 누구인지” 확인하는 과정이다.
- Authorization은 “인증된 사용자가 이 요청을 수행할 권한이 있는지” 확인하는 과정이다.
- JwtFilter는 주로 Authentication을 준비한다.
- Spring Security의 인가 Filter 또는 권한 규칙이 Authorization을 수행한다.

### Controller까지 이어지는 흐름

```text
OPTIONS Preflight
    ↓ CORS 허용 여부 확인
실제 GET /blogs/index
    ↓ Authorization: Bearer Access Token
Spring Security Filter Chain
    ↓
JwtFilter에서 토큰 검증 성공
    ↓
SecurityContext에 Authentication 저장
    ↓
DispatcherServlet(Front Controller)
    ↓
BlogController.index()
    ↓
BlogService.list()
    ↓
Spring Data JPA Repository
    ↓
SimpleJpaRepository
    ↓
Hibernate SQL 생성·실행
    ↓
DB 조회 결과 반환
```

화면의 실행 로그에서도 OPTIONS 요청과 Preflight 처리 이후 실제 GET 요청이 이어졌고, JwtFilter가 Bearer 토큰을 검증한 뒤 BlogController, BlogService, JPA Repository, Hibernate SQL 흐름으로 넘어가는 것을 확인했다.

### 핵심 포인트

> CORS Preflight 실패와 JWT 인증 실패는 서로 다른 문제다. OPTIONS가 통과해야 브라우저가 실제 GET 요청을 보낼 수 있고, 그 다음에 JwtFilter가 Access Token을 검증한다.

> SecurityContext에 Authentication이 저장되어야 이후 인가 처리와 Controller에서 현재 사용자를 알 수 있다.

## 핵심 코드

아래는 실행 화면에서 확인한 JWT 생성 방식과 같은 핵심 구조를 복습하기 위한 코드다. Secret 값 자체는 코드와 로그에 노출하지 않는다.

```java
public String createToken(String subject, long expirationMillis) {
    Date now = new Date();
    Date expiration = new Date(now.getTime() + expirationMillis);

    return Jwts.builder()
            .setSubject(subject)
            .setIssuedAt(now)
            .setExpiration(expiration)
            .signWith(getSecretKey())
            .compact();
}
```

# 🧠 오늘 이해한 핵심

- Filter, Interceptor, AOP는 모두 공통 기능을 처리하지만, Filter는 Servlet 요청, Interceptor는 MVC Handler, AOP는 Spring Bean 메서드를 기준으로 실행된다는 차이를 정리했다.
- @Valid는 Controller 진입 경계에서 DTO의 형식과 기본 조건을 검사하고, 이메일 중복이나 권한 확인 같은 비즈니스 규칙은 Service와 Domain에서 별도로 판단해야 한다.
- JWT는 Claim을 설정한 뒤 Secret Key로 서명하여 생성하고, 요청마다 JwtFilter가 Signature와 Expiration을 검증한 뒤 Authentication을 SecurityContext에 저장한다.
- CORS Preflight의 OPTIONS 요청이 먼저 통과해야 실제 GET 요청이 실행되며, 이후 인증 성공 요청만 Controller와 JPA 처리 흐름으로 이어진다.

# 🔍 복습할 부분

- Filter → SecurityFilterChain → JwtFilter → DispatcherServlet로 이어지는 실행 순서와, Interceptor·AOP가 각각 어느 시점에 개입하는지 다시 그려본다.
- @NotNull, @NotEmpty, @NotBlank, @Email, @Size의 차이와 @Valid 실패 시 발생하는 예외·HTTP 400 응답 흐름을 확인한다.
- JJWT 버전에 따른 setSubject()/subject() 차이와 signWith(), compact(), JWT 파싱·검증 예외를 다시 정리한다.
- Refresh Token Redis 저장, 재발급, Rotation, 로그아웃 이후 기존 Access Token 처리 방식의 차이를 비교한다.

# 🔄 함께 복습한 내용

- **입력값 Validation과 비즈니스 검증**: DTO의 @Valid는 null, 형식, 길이 같은 요청 자체의 조건을 검사한다. 이메일 중복, 재고, 작성자 여부처럼 현재 상태가 필요한 판단은 Service와 Domain에서 검증한다.
- **인증과 인가**: 인증은 사용자가 누구인지 확인하는 과정이고, 인가는 인증된 사용자가 해당 기능을 사용할 권한이 있는지 확인하는 과정이다. JWT 검증은 인증의 근거를 만들고, 권한 규칙은 인가를 담당한다.
- **JPA CRUD 테스트와 SQL 반영 시점**: save()는 엔티티를 영속성 컨텍스트에 등록하고, 변경 감지는 트랜잭션 안에서 엔티티 변화를 추적한다. flush()가 SQL을 DB에 전송하는 시점을 앞당길 수 있으며, 테스트 트랜잭션 롤백은 실행한 변경을 정리한다.
- **연관관계와 삭제 전파**: CascadeType.REMOVE는 부모 엔티티 삭제가 자식 삭제로 전파되는 상황을, orphanRemoval = true는 부모 컬렉션에서 자식이 고아가 된 상황을 중심으로 동작한다. EAGER와 LAZY는 연관 데이터를 언제 조회하는지의 차이이며, 조회 방식에 따라 N+1 문제가 발생할 수 있다.

## 1. DevOps와 CI/CD: 개발과 운영을 하나의 흐름으로 연결하기

### 개념

DevOps는 Development와 Operations를 결합한 문화와 방법론이다. 단순히 개발자와 운영자가 같은 팀에 있는 것을 의미하지 않고, 개발부터 배포와 운영까지의 과정을 자동화하고 연결하는 것을 목표로 한다.

CI/CD는 DevOps를 실천하기 위한 대표적인 자동화 방식이다.

|구분|의미|담당 범위|
|---|---|---|
|DevOps|개발과 운영을 연결하는 문화와 방법론|협업, 자동화, 피드백, 운영 책임|
|CI|Continuous Integration|코드 통합, Build, Test 자동화|
|CD|Continuous Delivery 또는 Deployment|검증된 결과물을 배포 가능한 상태로 만들거나 서버에 배포|

Continuous Delivery는 배포 가능한 상태까지 자동으로 준비한 뒤 실제 배포를 승인할 수 있는 방식이다. Continuous Deployment는 테스트를 통과한 코드를 운영 서버까지 자동으로 배포하는 방식이다.

### 동작 흐름

```text
코드 작성
    ↓
Commit 및 Push
    ↓
Workflow 또는 Webhook 실행
    ↓
최신 코드 Checkout
    ↓
Build
    ↓
Test
    ↓
JAR 또는 Docker Image 생성
    ↓
서버에 Deploy
    ↓
로그·포트·브라우저로 검증
```

### 핵심 코드

GitHub Actions Workflow는 프로젝트 루트의 `.github/workflows/deploy.yml`에 작성한다.

```yaml
name: CI

on:
  push:
    branches:
      - main
  workflow_dispatch:

jobs:
  build-test:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Set up JDK
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'

      - name: Build and Test
        run: |
          chmod +x gradlew
          ./gradlew clean build
```

`Workflow`는 전체 자동화 파일이고, `Job`은 실행할 작업의 묶음이다. `Step`은 실제 명령이나 Action이 실행되는 단위이며, `Runner`는 Job을 실행하는 컴퓨터 환경이다.

### 핵심 포인트

> CI는 코드를 통합하고 검증하는 과정이고, CD는 검증된 결과물을 배포하는 과정이다. DevOps는 이 전체 흐름을 협업과 자동화로 연결하는 개념이다.

## 2. Git과 Maven·Gradle: 변경 사항을 추적하고 빌드 결과물 만들기

### 개념

Git은 코드 변경 이력을 관리하는 분산 버전 관리 도구다. GitHub는 Git Repository를 원격에 저장하고 협업할 수 있게 해주는 서비스다.

### Git의 네 가지 영역

|영역|설명|다음 단계|
|---|---|---|
|Working Directory|실제 파일을 수정하는 공간|`git add`|
|Staging Area|다음 Commit에 포함할 변경 사항을 선택하는 공간|`git commit`|
|Local Repository|Commit 이력이 로컬 `.git`에 저장되는 공간|`git push`|
|Remote Repository|GitHub 등에 저장되어 팀원과 공유하는 공간|협업 및 배포|

### 동작 흐름

```text
Working Directory
    ↓ git add
Staging Area
    ↓ git commit
Local Repository
    ↓ git push
Remote Repository
```

### 핵심 코드

```bash
git init
git add .
git commit -m "Initial commit"
git branch -M main
git remote add origin https://github.com/<username>/<repository>.git
git push -u origin main
```

원격 저장소와 브랜치 정보를 확인할 때는 목적에 따라 명령어가 다르다.

|명령어|확인 대상|
|---|---|
|`git branch -vv`|로컬 브랜치, 추적 중인 원격 브랜치, 앞서거나 뒤처진 상태|
|`git remote -v`|등록된 원격 저장소의 Fetch·Push URL|

`git fetch`와 `git pull`의 차이도 구분해야 한다.

|명령어|동작|
|---|---|
|`git fetch`|원격 변경 이력만 가져오며 현재 작업 파일에는 바로 반영하지 않음|
|`git pull`|원격 변경 이력을 가져온 뒤 현재 브랜치에 통합함|

### Maven과 Gradle 비교

|명령어|수행 작업|결과|
|---|---|---|
|`mvn clean install`|기존 결과물 삭제, Build·Test·Package 수행|패키지를 Maven 로컬 저장소에 설치|
|`./gradlew clean build`|기존 결과물 삭제 후 Gradle Wrapper로 Build|일반적으로 Test를 포함한 빌드 결과물 생성|
|`./gradlew test`|테스트만 실행|테스트 결과 확인|

`mvn clean install`의 `install`은 운영 서버에 프로그램을 설치한다는 뜻이 아니다. 생성된 패키지를 `~/.m2/repository`에 등록해 다른 로컬 Maven 프로젝트가 사용할 수 있도록 한다는 의미다. 또한 `clean install`은 CI라는 별도 옵션이 아니라 Maven의 빌드 단계를 연속으로 실행하는 명령이다.

### 핵심 포인트

> Git은 변경 사항을 단계적으로 관리하고, Maven·Gradle은 소스 코드를 테스트 가능한 패키지나 실행 결과물로 변환한다.

## 3. Docker: 빌드 결과물을 일관된 환경에서 실행하기

### 개념

Docker는 애플리케이션 실행에 필요한 코드, 라이브러리, 설정을 Image로 묶고 Container에서 격리해 실행하는 도구다.

|구성 요소|역할|
|---|---|
|Docker|Image와 Container를 생성·실행·관리하는 도구|
|Image|Container를 만들기 위한 설계도 또는 템플릿|
|Container|Image를 기반으로 실제 실행 중인 독립 공간|
|Host|Docker와 Container가 실행되는 실제 컴퓨터 또는 EC2 서버|

하나의 Image로 여러 개의 Container를 만들 수 있다. Image가 설계도라면 Container는 그 설계도를 실행한 결과다.

### 동작 흐름

```text
Dockerfile
    ↓ docker build
Docker Image
    ↓ docker run
Docker Container
    ↓
애플리케이션 실행
```

### Dockerfile의 실행 시점

|명령어|실행 시점|역할|
|---|---|---|
|`RUN`|Image Build 시점|패키지 설치, 컴파일, 테스트 등 실행|
|`CMD`|Container 시작 시점|기본 실행 명령 또는 기본 인자 지정|
|`ENTRYPOINT`|Container 시작 시점|실행할 기본 프로그램을 지정|

`RUN`의 결과는 Image Layer에 반영된다. 반면 `CMD`와 `ENTRYPOINT`는 Image를 Build할 때 실행되는 명령이 아니라, 해당 Image로 Container가 시작될 때 실행할 명령을 지정한다.

### 핵심 코드

Gradle로 JAR를 먼저 생성한 뒤 Docker Image에 복사하는 Spring Boot 예시다.

```dockerfile
FROM eclipse-temurin:21-jdk-alpine

COPY ./build/libs/*SNAPSHOT.jar project.jar

ENTRYPOINT ["java", "-jar", "project.jar"]
```

실행 명령은 다음과 같다.

```bash
./gradlew clean build

docker build -t backend:local .

docker run -d -p 8080:8080 --name backend backend:local

docker ps
docker logs backend
```

`docker build -t backend:local .`에서 `-t`는 Image 이름과 태그를 지정하는 옵션이다. `backend`는 Image 이름이고 `local`은 태그다. 마지막 `.`은 현재 디렉터리를 Build Context로 사용하며, 기본적으로 현재 디렉터리의 Dockerfile을 찾도록 한다.

`docker run -d -p 8080:8080 backend:local`에서 `-p`의 형식은 `호스트 포트:컨테이너 포트`다. 따라서 호스트의 8080 포트와 Container의 8080 포트를 연결하고, 백그라운드에서 실행한다.

### Image Tag와 `latest`

Image 이름에 태그를 생략하면 기본적으로 `latest` 태그가 사용된다.

```bash
docker pull nginx
docker build -t backend .
```

위 명령은 각각 `nginx:latest`, `backend:latest`를 사용하는 것과 같다. 그러나 `latest`는 항상 시간상 최신 버전임을 보장하는 특별한 기능이 아니다. 단순히 `latest`라는 이름의 태그일 뿐이다.

운영 환경에서는 다음처럼 추적 가능한 태그를 사용하는 것이 안전하다.

```text
backend:1.0.0
backend:20260910
backend:<git-commit-sha>
```

### 핵심 포인트

> Image는 실행 환경의 설계도이고 Container는 실행 결과다. `RUN`은 Build 시점에, `CMD`와 `ENTRYPOINT`는 Container 시작 시점에 동작한다.

## 4. AWS 실행 기반: EC2에 접근하고 권한을 분리하기

### 개념

AWS에서는 필요한 서버와 네트워크 자원을 클라우드에서 생성해 사용할 수 있다. EC2는 가상 서버이며, AMI는 EC2를 생성할 때 사용하는 운영체제와 기본 설정의 이미지다.

|구성 요소|역할|학습에서의 연결|
|---|---|---|
|AMI|EC2 생성에 사용할 운영체제 이미지|Ubuntu Linux Server 선택|
|EC2|AWS에서 사용하는 가상 서버|Docker, Jenkins, 애플리케이션 실행|
|IAM|AWS 사용자·정책·권한 관리 서비스|ECR 접근 권한 관리|
|IAM Role|AWS 리소스에 연결하는 권한 주체|EC2의 ECR Pull 권한|
|Security Group|EC2의 Inbound·Outbound 트래픽 제어|SSH·HTTP·서비스 포트 허용|
|Key Pair|EC2 SSH 접속을 위한 공개키·개인키 쌍|`.pem` 파일로 접속|

실습에서 Linux AMI를 선택한 이유는 서버 운영에 필요한 기능 중심으로 구성되어 상대적으로 가볍고, GUI 등 불필요한 리소스 부담이 적기 때문이다. 다만 모든 상황에서 Linux가 무조건 더 빠르다는 의미는 아니다.

### EC2 생성과 접속 흐름

```text
AMI 선택
    ↓
인스턴스 유형 선택
    ↓
Key Pair 생성 또는 선택
    ↓
Security Group 포트 설정
    ↓
EC2 실행 및 Public IPv4 확인
    ↓
SSH 또는 EC2 Instance Connect로 접속
```

### 핵심 코드

Ubuntu AMI 기준 접속 예시다.

```bash
chmod 400 ~/Downloads/devops-server-key.pem

ssh -i ~/Downloads/devops-server-key.pem ubuntu@<EC2_PUBLIC_IP>
```

EC2에 Docker를 설치하고 사용자를 Docker 그룹에 추가한다.

```bash
sudo apt update
sudo apt install -y docker.io docker-compose-v2

sudo usermod -aG docker ubuntu
newgrp docker

docker --version
docker compose version
```

`apt`는 Ubuntu와 Debian 계열의 패키지 관리자이고, `sudo`는 관리자 권한으로 명령을 실행하는 명령어다.

Security Group에서 실습에 사용하는 대표 포트는 다음과 같다.

|용도|포트|주의점|
|---|---|---|
|SSH|22|가능한 한 내 IP로 제한|
|HTTP|80|공개 웹 서비스에 사용|
|Jenkins|8080|실습 환경에서 외부 접근 허용 가능|
|Spring Boot|8088 또는 8080|Jenkins와 포트가 겹치지 않도록 확인|

Jenkins와 Spring Boot를 같은 EC2에서 실행할 때 두 서비스가 모두 8080을 사용하면 포트 충돌이 발생한다. 애플리케이션 포트를 8088로 변경하거나 Jenkins 포트를 변경하고, 필요하면 Reverse Proxy 또는 별도 서버를 사용한다.

### 핵심 포인트

> EC2는 실행 공간이고, Security Group은 네트워크 접근을 제어하며, IAM Role은 서버가 AWS 리소스에 접근할 수 있도록 권한을 부여한다. Key Pair와 Secret은 코드 저장소에 올리지 않는다.

## 5. GitHub Actions와 ECR: Docker Image 자동 배포하기

### 개념

GitHub Actions는 GitHub 저장소에서 Workflow를 실행하는 자동화 기능이다. Hosted Runner를 사용하면 별도의 CI 서버를 직접 설치하지 않고도 Build·Test·Deploy를 실행할 수 있다.

ECR은 AWS가 제공하는 Docker Image 저장소다. GitHub Actions가 Image를 ECR에 Push하고, EC2가 ECR에서 Image를 Pull한 뒤 Container를 실행하는 구조로 사용할 수 있다.

### GitHub Actions 구성 요소

|구성 요소|역할|
|---|---|
|Workflow|자동화 전체를 정의한 YAML 파일|
|Job|하나의 실행 작업 묶음|
|Step|순서대로 실행되는 개별 단계|
|Runner|Job을 실제로 실행하는 컴퓨터 환경|

### Secret과 IAM Role 비교

|구분|GitHub Actions Secret|EC2 IAM Role|
|---|---|---|
|사용 위치|GitHub Actions Runner|EC2 인스턴스|
|목적|SSH Key, AWS Key, 설정 파일 등 비밀 값 전달|EC2가 ECR 등 AWS 리소스에 접근|
|관리 방식|Repository Settings에 저장|EC2에 Role 연결|
|주의점|로그에 출력하지 않음|운영 환경에서는 최소 권한 사용|

실습에서는 GitHub Actions용 IAM 사용자에 ECR 권한을 부여하고 Access Key와 Secret Access Key를 GitHub Secret에 저장했다. EC2에는 IAM Role을 연결해 ECR Image를 Pull하도록 구성한다. 운영 환경에서는 `AmazonEC2ContainerRegistryFullAccess`보다 필요한 Push·Pull 권한만 부여하는 것이 안전하다.

### 동작 흐름

```text
GitHub main 브랜치 Push
    ↓
GitHub Actions Workflow 실행
    ↓
Runner가 코드 Checkout
    ↓
Gradle Build 및 Test
    ↓
Docker Image Build
    ↓ Commit SHA를 Image Tag로 사용
ECR에 Image Push
    ↓
EC2가 IAM Role로 ECR Image Pull
    ↓
기존 Container 중지 및 삭제
    ↓
새 Image로 Container 실행
    ↓
docker ps·docker logs·브라우저 확인
```

### 핵심 코드

GitHub Actions에서 Docker Image를 Build하고 ECR에 Push하는 학습용 Workflow다.

```yaml
name: Build and Push Docker Image

on:
  push:
    branches:
      - main
  workflow_dispatch:

jobs:
  docker:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Set up JDK 21
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'

      - name: Build JAR
        run: |
          chmod +x gradlew
          ./gradlew clean build

      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: ap-northeast-2

      - name: Login to Amazon ECR
        id: login-ecr
        uses: aws-actions/amazon-ecr-login@v2

      - name: Build and Push Image
        env:
          REGISTRY: ${{ steps.login-ecr.outputs.registry }}
          REPOSITORY: devops-server
          IMAGE_TAG: ${{ github.sha }}
        run: |
          docker build -t $REGISTRY/$REPOSITORY:$IMAGE_TAG .
          docker push $REGISTRY/$REPOSITORY:$IMAGE_TAG
```

EC2에서 ECR Image를 Pull하고 Container를 실행한다.

```bash
docker pull <ECR_REGISTRY>/<REPOSITORY>:<IMAGE_TAG>

docker stop backend || true
docker rm backend || true

docker run -d \
  --name backend \
  -p 8080:8080 \
  <ECR_REGISTRY>/<REPOSITORY>:<IMAGE_TAG>

docker ps
docker logs backend
```

ECR Credential Helper를 사용하면 Docker가 ECR 인증을 처리하도록 설정할 수 있다.

```bash
sudo apt update
sudo apt install -y amazon-ecr-credential-helper

mkdir -p ~/.docker
```

`~/.docker/config.json` 파일에 다음 내용을 작성한다.

```json
{
  "credsStore": "ecr-login"
}
```

이 설정은 사용자별로 적용된다. `ubuntu` 사용자가 Docker를 실행하는 경우와 `jenkins` 사용자가 Docker를 실행하는 경우 Docker 설정 경로가 다를 수 있다.

### JAR 배포와 Docker 배포 비교

|방식|CI 결과물|EC2 배포 방식|특징|
|---|---|---|---|
|JAR 배포|`build/libs/*.jar`|SCP 전송 후 `java -jar` 실행|단순하지만 프로세스 관리 필요|
|Docker 배포|Docker Image|ECR Pull 후 Container 실행|실행 환경 재현성과 버전 관리에 유리|

민감한 `application.yml`은 Repository에 직접 Commit하지 않고 GitHub Secret으로 관리한다. 필요한 경우 Workflow 실행 중 Secret을 사용해 파일을 생성한다.

```bash
mkdir -p src/main/resources
printf '%s' "$APPLICATION_PROPERTIES" > src/main/resources/application.yml
```

### 핵심 포인트

> GitHub Actions는 Build와 Test를 실행하고, ECR은 Image를 저장하며, EC2는 Image를 Pull해 Container를 실행한다. Image Tag에 Commit SHA를 사용하면 어떤 코드가 배포되었는지 추적하기 쉽다.

## 6. Jenkins: 서버형 CI/CD와 Pipeline as Code

### 개념

Jenkins는 서버에 설치해 사용하는 무료 오픈 소스 CI/CD 자동화 도구다. 개발자가 GitHub에 Push하면 Webhook으로 이벤트를 전달받고, Jenkins가 Checkout·Build·Test·Deploy를 실행한다.

Jenkins의 Job은 Jenkins가 수행해야 할 작업의 기본 단위다.

### Jenkins 설치와 초기 설정

Docker 설치 후 Jenkins가 Docker를 사용할 수 있도록 Jenkins 사용자를 Docker 그룹에 추가한다.

```bash
sudo apt update
sudo apt install -y fontconfig openjdk-21-jdk

# Jenkins 공식 저장소와 GPG Key 등록 후
sudo apt update
sudo apt install -y jenkins

sudo usermod -aG docker jenkins

sudo systemctl start jenkins
sudo systemctl enable jenkins
sudo systemctl restart jenkins
sudo systemctl status jenkins

sudo cat /var/lib/jenkins/secrets/initialAdminPassword
```

초기 설정은 다음 순서로 진행한다.

```text
http://<EC2_PUBLIC_IP>:8080 접속
    ↓
초기 관리자 비밀번호 입력
    ↓
Install suggested plugins 선택
    ↓
관리자 계정 생성
    ↓
Stage View Plugin 설치
    ↓
Jenkins 재시작
```

### Freestyle Project와 Pipeline 비교

|구분|Freestyle Project|Pipeline|
|---|---|---|
|설정 방식|웹 화면에서 입력|Jenkinsfile에 코드로 정의|
|장점|간단한 작업을 빠르게 구성|복잡한 Build·Test·Deploy 관리|
|변경 이력|Jenkins 내부 설정에 의존|Git으로 버전 관리 가능|
|확장성|복잡한 흐름에 불리함|조건·반복·병렬·승인 단계 구성 가능|
|적합한 경우|단순 Shell 실행|실무 CI/CD 파이프라인|

### 핵심 코드

프로젝트 루트에 `Jenkinsfile`을 작성한다.

```groovy
pipeline {
    agent any

    stages {
        stage('Build') {
            steps {
                sh 'chmod +x gradlew'
                sh './gradlew clean build'
            }
        }

        stage('Test') {
            steps {
                sh './gradlew test'
            }
        }

        stage('Deploy') {
            steps {
                sh 'echo "deploy application"'
            }
        }
    }
}
```

`Pipeline script from SCM`을 선택하면 Jenkins가 GitHub Repository에서 `Jenkinsfile`을 가져와 실행할 수 있다.

### GitHub Webhook 연결

```text

    ↓
```

실습 환경에서는 HTTP를 사용할 수 있지만 운영 환경에서는 HTTPS와 유효한 인증서를 사용하고 SSL 검증을 활성화해야 한다.

### GitHub Actions와 Jenkins 비교

|항목|GitHub Actions|Jenkins|
|---|---|---|
|실행 환경|GitHub Hosted Runner 또는 Self-hosted Runner|직접 설치한 Jenkins 서버|
|초기 설치|Hosted Runner 사용 시 별도 CI 서버 불필요|EC2 등 별도 실행 환경 필요|
|관리 부담|Workflow와 Secret 중심|서버·Plugin·보안·백업 관리|
|GitHub 연동|Push·PR과 자연스럽게 연동|Webhook·SCM 설정 필요|
|확장성|YAML과 Marketplace Action 활용|Pipeline과 Plugin으로 세밀하게 구성|
|적합한 환경|GitHub 기반 프로젝트의 빠른 자동화|사내망·폐쇄망·높은 환경 통제 필요|

### 핵심 포인트

> GitHub Actions는 빠르게 시작하기 좋고, Jenkins는 별도 서버를 운영하는 대신 실행 환경과 Pipeline을 세밀하게 통제할 수 있다.

# 🐛 문제 해결

## 문제

Dockerfile 명령어의 실행 시점과 Docker 명령어의 역할이 혼동되기 쉬웠다. 또한 Image Tag 생략, `mvn clean install`, Jenkins와 Spring Boot의 포트 사용도 주의가 필요했다.

### 원인

- `RUN`, `CMD`, `ENTRYPOINT`가 모두 명령어처럼 보이지만 실행 시점이 다름
- `latest`라는 이름 때문에 항상 최신 버전이라고 생각하기 쉬움
- Maven의 `install`을 CI 설정이나 운영 서버 설치로 오해하기 쉬움
- Jenkins와 Spring Boot가 기본 포트 8080을 동시에 사용할 수 있음

### 해결

|혼동 지점|정확한 기준|
|---|---|
|`RUN`|Image Build 중 실행|
|`CMD`|Container 시작 시 실행되는 기본 명령 또는 인자|
|`ENTRYPOINT`|Container 시작 시 실행되는 기본 실행 프로그램|
|`-t`|Image 이름과 Tag 지정 옵션이며 반드시 소문자 사용|
|Tag 생략|기본적으로 `latest` 사용|
|`latest`|최신 버전 보장이 아닌 태그 이름|
|`mvn clean install`|`clean`과 `install` 빌드 단계 실행, CI 옵션이 아님|
|`install`|운영 서버 설치가 아니라 Maven 로컬 저장소에 패키지 등록|
|포트 충돌|Jenkins 또는 애플리케이션의 포트를 변경하거나 Reverse Proxy 사용|

EC2에 접속되지 않거나 Container가 바로 종료될 때는 다음 순서로 확인한다.

```bash
docker ps -a
docker logs backend

ps -ef | grep java
lsof -i :8080
sudo systemctl status jenkins
```

또한 EC2의 Running 상태, Public IPv4, Security Group의 Inbound 규칙, 애플리케이션이 실제로 사용하는 포트를 함께 확인한다.

### 배운 점

> 명령어를 단순히 외우기보다 Build 시점, Container 시작 시점, 서버 실행 시점으로 나누어 이해하면 Docker와 CI/CD 흐름을 정확하게 설명할 수 있다.

# 🔄 함께 복습한 내용

- **Spring Security와 요청 처리 흐름**  
    요청은 Servlet Filter와 Spring Security의 `SecurityFilterChain`을 거친 뒤 `DispatcherServlet`으로 전달된다. `JwtFilter`는 인증 토큰을 검증해 SecurityContext에 인증 정보를 설정하고, Interceptor는 Controller 실행 전후에 개입하며 AOP는 프록시 객체의 메서드 실행 전후를 감싼다.
    
- **Validation과 HTTP 400 응답**  
    `@NotNull`은 null만 허용하지 않고, `@NotEmpty`는 null·빈 값을 제한하며, `@NotBlank`는 공백만 있는 문자열도 제한한다. `@Email`은 이메일 형식을 검사하고 `@Size`는 문자열·컬렉션 등의 크기를 검사한다. `@Valid` 검증에 실패하면 일반적으로 `MethodArgumentNotValidException`이 발생하고 예외 처리 과정을 거쳐 HTTP 400 응답이 반환된다.
    
- **JWT와 JJWT 버전 차이**  
    JJWT 버전에 따라 Subject 설정 메서드가 `setSubject()` 또는 `subject()`로 달라질 수 있다. `signWith()`로 서명하고 `compact()`으로 문자열을 생성하며, 파싱 과정에서는 서명·만료 시간을 검증하고 `ExpiredJwtException`, `MalformedJwtException`, `SignatureException` 등의 예외를 확인해야 한다.
    
- **Refresh Token과 Redis**  
    Refresh Token은 Redis에 사용자나 토큰 식별자와 함께 저장하고 TTL을 설정해 관리한다. 재발급 시 기존 Refresh Token을 폐기하고 새 토큰을 저장하는 Rotation을 적용할 수 있으며, 로그아웃 시 Redis의 Refresh Token을 삭제한다. 별도 차단 정책이 없다면 이미 발급된 Access Token은 만료 전까지 유효할 수 있으므로 블랙리스트나 토큰 버전 검증 등의 정책이 필요하다.
    
- **DevOps·CI/CD와 Git**  
    DevOps는 개발과 운영을 연결하는 문화와 방법론이고, CI는 코드 통합·Build·Test 자동화, CD는 검증된 결과물의 배포 자동화에 해당한다. Git은 `Working Directory → Staging Area → Local Repository → Remote Repository` 순서로 변경 사항을 관리하며, `fetch`는 가져오기만 하고 `pull`은 가져온 내용을 현재 브랜치에 통합한다.
    
- **Docker와 빌드 도구**  
    Docker Image는 Container의 설계도이고 Container는 Image의 실행 결과다. `docker build`는 Image를 만들고 `docker run`은 Container를 생성·실행한다. Image Tag를 생략하면 `latest`가 사용되지만 최신 버전을 보장하지 않으며, `mvn clean install`은 CI 옵션이 아니라 Maven 빌드와 로컬 저장소 설치 단계다.
    
- **AWS·GitHub Actions·ECR·Jenkins**  
    AMI는 EC2 생성용 운영체제 이미지, EC2는 가상 서버, IAM은 권한 관리, Security Group은 네트워크 접근 제어, Key Pair는 SSH 접속 수단이다. GitHub Actions는 Hosted Runner로 별도 CI 서버 없이 시작할 수 있고, Jenkins는 별도 서버 구축이 필요하지만 Pipeline과 Plugin을 통해 실행 환경을 세밀하게 제어할 수 있다.

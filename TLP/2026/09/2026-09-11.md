## 📌 오늘 학습 계획

1. **Servlet Filter의 요청 처리 흐름 파악**
    - 클라이언트 요청이 Servlet Filter Chain과 `DispatcherServlet`을 거쳐 Controller에 도달하는 순서를 확인한다.
    - `chain.doFilter()` 호출 전후의 실행 흐름과 Filter가 요청·응답에 개입하는 위치를 정리한다.
    - `REQUEST`, `FORWARD`, `INCLUDE`, `ERROR`, `ASYNC`의 차이를 확인한다.
2. **OncePerRequestFilter의 중복 실행 방지 원리 확인**
    - `GenericFilterBean`과 `OncePerRequestFilter`의 상속 구조, 구현 메서드, 중복 실행 제어 여부를 비교한다.
    - 요청 속성에 실행 표식을 저장해 `doFilterInternal()`의 재실행을 제어하는 과정을 추적한다.
    - `ASYNC`·`ERROR` 디스패치 설정에 따라 실행 범위가 달라지는 이유를 확인한다.
    - 프리플라이트와 실제 요청, 오류 재디스패치, Filter 이중 등록을 실제 중복 실행과 구분한다.
3. **Spring Security의 인증·인가 구조 이해**
    - `DelegatingFilterProxy`, `FilterChainProxy`, `SecurityFilterChain`의 역할과 연결 관계를 정리한다.
    - `Authentication`, `SecurityContext`, `SecurityContextHolder`, `AuthenticationManager`의 역할을 요청 흐름에 맞춰 확인한다.
    - JWT의 서명·만료 검증부터 `Authentication` 생성과 `SecurityContext` 저장까지의 순서를 학습한다.
    - `permitAll()`과 Filter 실행 생략의 차이, 인증 실패 401과 권한 부족 403의 차이를 구분한다.
    - CORS 프리플라이트와 CSRF 보호가 Security Filter Chain에서 처리되는 위치를 확인한다.
4. **Redis 기본 사용과 TTL 확인**
    - Redis의 String 자료구조를 중심으로 `SET`, `GET`, `EXISTS`, `DEL` 명령을 실행한다.
    - `EX`, `TTL`, `PTTL`을 사용해 키의 만료 시간과 `TTL -1`, `TTL -2`의 의미를 확인한다.
    - `SET NX EX`를 사용해 키가 없을 때만 저장하면서 만료 시간을 함께 설정하는 방식을 확인한다.
    - Spring Boot의 Redis 연결 설정과 `StringRedisTemplate`을 이용한 저장·조회·삭제 방법을 작성한다.
5. **Spring Security와 Redis의 연결 방식 정리**
    - Refresh Token 저장과 Access Token 폐기 목록에 Redis TTL을 적용하는 흐름을 확인한다.
    - 로그아웃 이후 Refresh Token과 이미 발급된 Access Token이 각각 어떻게 처리되는지 구분한다.
    - `OncePerRequestFilter`의 재실행 제어와 별도 HTTP 요청의 중복 처리를 막는 멱등성의 차이를 정리한다.
    - Redis의 `SET NX EX`와 분산 락이 각각 보장하는 범위를 구분한다.

## 🤔 예상되는 어려움

- `OncePerRequestFilter`의 “한 번 실행”을 모든 디스패치를 포함한 HTTP 요청 전체의 단 한 번으로 오해할 수 있다.
- `permitAll()`이 설정된 경로에서는 커스텀 JWT Filter도 실행되지 않는다고 혼동할 수 있다.
- JWT 검증, `Authentication` 생성, `SecurityContext` 저장의 책임과 실행 순서가 헷갈릴 수 있다.
- Redis의 TTL·`SET NX EX`가 캐시 정합성, 요청 멱등성, 분산 락까지 모두 해결한다고 오해할 수 있다.
- 인증 실패와 권한 부족, CORS 차단과 CSRF 거부가 모두 비슷한 요청 실패로 보일 수 있다.

## 💡 해결 전략

- 요청 메서드·URI·`DispatcherType`·Filter 인스턴스를 함께 기록하고 `REQUEST`, `ASYNC`, `ERROR` 실행 결과를 대조한다.
- 공개 경로 요청도 Security Filter Chain을 통과하는 과정을 직접 따라가며 `permitAll()`이 적용되는 인가 단계를 표시한다.
- 정상 토큰, 만료 토큰, 토큰이 없는 요청을 기준으로 JWT 검증부터 `SecurityContext` 저장까지의 흐름을 각각 작성한다.
- TTL, 조건부 저장, 멱등키, 분산 락을 적용한 작은 사례를 나누고 각 방식이 막을 수 있는 문제와 막지 못하는 문제를 비교한다.
- 응답 상태 코드와 브라우저 콘솔·서버 로그를 함께 확인해 401, 403, CORS, CSRF의 발생 지점을 구분한다.

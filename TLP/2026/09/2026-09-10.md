## 🤔 예상되는 어려움

- Git의 Commit, Push, Fetch, Pull이 각각 다른 저장 영역과 동작을 가진다는 점이 혼동될 수 있다.
- Docker Image와 Container의 관계 및 컨테이너 포트와 호스트 포트의 연결 구조가 헷갈릴 수 있다.
- Dockerfile의 RUN과 CMD, ENTRYPOINT가 실행되는 시점을 구분하기 어려울 수 있다.
- 이미지 Tag를 생략했을 때 latest가 적용되는 규칙과 실제 최신 버전 여부가 혼동될 수 있다.
- Maven의 install이 운영 서버 설치가 아니라 로컬 저장소 등록이라는 점이 헷갈릴 수 있다.
- AWS IAM User와 IAM Role의 사용 목적을 구분하기 어려울 수 있다.
- EC2의 Public IP, Security Group, SSH Key가 모두 연결되어야 접속된다는 점이 복잡할 수 있다.
- GitHub Actions YAML의 들여쓰기와 Workflow 실행 조건을 정확하게 작성하기 어려울 수 있다.
- GitHub Secret, AWS Access Key, EC2 Private Key를 안전하게 관리하는 방법이 낯설 수 있다.
- ECR Push와 EC2 Pull에 필요한 권한 및 인증 방식을 구분하기 어려울 수 있다.
- Jenkins 설치 과정에서 Java, Docker 권한, 서비스 상태, Plugin 설정이 서로 연결되어 있어 오류 원인을 찾기 어려울 수 있다.
- Jenkins와 Spring Boot가 동일한 8080 포트를 사용할 때 포트 충돌이 발생할 수 있다.
- 자동 배포가 실행되었더라도 실제 서버 프로세스와 브라우저 응답까지 확인해야 한다는 점을 놓칠 수 있다.

## 💡 해결 전략

- 모든 개념을 단독으로 외우기보다 Git → Build → Docker → AWS → CI/CD 순서의 전체 흐름으로 연결해 이해한다.
- 명령어를 실행하기 전에 명령어의 대상이 이미지인지 컨테이너인지, 로컬인지 원격인지 먼저 확인한다.
- Git은 작업 디렉터리, Staging Area, Local Repository, Remote Repository를 직접 그려가며 정리한다.
- Docker 명령어는 Image 관련 명령과 Container 관련 명령을 나누어 표로 정리한다.
- Dockerfile 명령어는 이미지 Build 시점과 컨테이너 시작 시점으로 구분해 암기한다.
- `docker build -t backend:local .`과 `docker run -d -p 8080:8080 backend:local`을 각 옵션 단위로 분해해 설명한다.
- Maven과 Gradle 명령어는 clean, build, test, install이 각각 무엇을 삭제·생성·실행·저장하는지 비교한다.
- AWS 설정은 IAM 권한 → EC2 생성 → Security Group → Key Pair → SSH 접속 순서로 확인한다.
- 접속 오류가 발생하면 인스턴스 상태, Public IP, Security Group, 포트, 프로세스 순서로 점검한다.
- GitHub Actions는 Workflow 파일 위치, 이벤트 조건, Runner, Job, Step 순서로 나누어 확인한다.
- Secret 값은 코드와 로그에 출력하지 않고 이름과 주입 위치만 확인한다.
- ECR 오류는 IAM 권한, Repository URI, Region, Image Tag, Login 상태 순서로 점검한다.
- Jenkins 오류는 Java 설치, Docker 권한, Jenkins 서비스 상태, Plugin, Webhook 순서로 확인한다.
- Jenkins와 Spring Boot의 포트가 충돌하면 포트를 변경하거나 Reverse Proxy를 사용한다.
- 자동화 성공 여부는 실행 화면만 보지 않고 로그, 프로세스, 포트, 브라우저 응답까지 단계적으로 검증한다.
- 실습에서 사용한 FullAccess와 0.0.0.0/0 설정은 운영 환경에서 최소 권한과 접근 제한으로 개선한다.

## 📝 메모

- DevOps는 개발과 운영을 분리하는 것이 아니라 전체 흐름을 연결하는 방식이다.
- CI/CD의 핵심은 코드를 Push한 뒤 Build, Test, Deploy가 반복 가능하게 자동 실행되는 것이다.
- Git은 코드 변경 이력을 관리하고, Docker는 실행 환경을 이미지로 묶으며, AWS는 서버와 저장소를 제공한다.
- GitHub Actions는 별도 서버 설치 없이 시작하기 쉽고, Jenkins는 별도 서버 운영이 필요하지만 높은 통제력과 확장성을 제공한다.
- `RUN`은 이미지 생성 시 실행되고 `CMD`, `ENTRYPOINT`는 컨테이너 시작 시 실행된다.
- Docker 이미지 이름과 Tag를 생략하면 기본적으로 `latest`가 사용되지만, `latest`가 항상 최신 버전이라는 의미는 아니다.
- `docker build`의 Tag 옵션은 대문자 `-T`가 아닌 소문자 `-t`이다.
- `mvn clean install`은 CI 옵션이 아니라 기존 결과물을 삭제하고 빌드한 뒤 패키지를 Maven 로컬 저장소에 설치하는 명령이다.
- Ubuntu Linux AMI는 서버 운영에 필요한 기능 중심이라 상대적으로 가볍고 리소스 부담이 적다.
- EC2에 Jenkins와 Spring Boot를 함께 실행할 때 기본 포트 8080이 겹치지 않도록 주의한다.
- AWS Access Key, Secret Access Key, PEM Private Key, 실제 application 설정 값은 Git 저장소에 직접 올리지 않는다.
- ECR을 사용하는 Docker 배포에서는 GitHub Actions가 Image를 Push하고 EC2가 Image를 Pull한다.
- 배포가 끝났다는 판단은 자동화 도구의 성공 표시만으로 하지 않고 서버에서 실제 애플리케이션이 실행되고 요청에 응답하는지 확인한 뒤 내린다.
